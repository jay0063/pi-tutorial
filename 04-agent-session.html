AgentSession 与装配
Chapter 04 · pi-coding-agent

产品不是更大的循环，
而是一圈钩子

AgentSession 没有重新实现 agent loop。它用组合与钩子，把“会话落盘、上下文投影、系统提示、压缩、重试、扩展、工具权限”缠在循环外面。这一章看它如何不改循环却改变行为。

4.1它到底负责什么

把 AgentSession 当成一个“运行时容器”。它持有五个协作者，自己只做编排：

按职责列一下它的“产品逻辑”：

  • 输入侧：扩展命令、输入拦截、技能/模板展开、图片缩放、流式期间排队。
  • 请求侧：压缩检查、before_agent_start、系统提示差量、工具装载、模型路由。
  • 运行侧：把 agent 事件持久化、转发给扩展与 UI、维护队列显示、记录嵌套工具调用。
  • 结束侧：自动重试、溢出恢复、阈值压缩、agent_before_settle 边界、空闲通知。

  • L516请求投影：每次请求前，把 agent.state.messages 换成会话投影，而不是直接改历史。
  • L517-519边界钩子、隐藏工具投影、强制系统提示投影。它们都是包装上一个钩子，形成责任链。

注意最后三组都是“包装”：const previous = this.agent.prepareRequest; this.agent.prepareRequest = async (...) => { ... previous?.(...) }。这允许不同子系统独立安装，不互相覆盖。读代码时看到 previousX，就要意识到可能还有更早的包装者。

4.3一次 prompt 的完整管道

prompt() 不是“把字符串丢给模型”。它是一条有十几个站点的管道，每一站都可能拦截或改写：

运行前：_prepareRun

它做四件事，顺序不能换：

  1. 如果上一条 assistant 消息导致上下文过大，先尝试压缩（包括被中止的响应）。
  2. 触发 before_agent_start，让扩展修改系统提示、模型或工具；扩展也可以直接返回附加消息。
  3. 归一化图片（按最终模型的输入限制缩放），并把缩放提示拼进用户文本。
  4. 把起始消息、待注入的 nextTurn 消息、扩展返回的消息排好序；如果系统提示有变化，先插一条 system patch。
为什么先压缩再跑 before_agent_start

压缩会改写模型可见的上下文；如果先跑扩展钩子，扩展基于旧上下文做的决策可能立刻失效。pi 选择“先把房间收拾好，再请客人进来”。

运行中：不是“一次 agent.prompt 就结束”

_startRun 调完 agent.prompt() 后进入一个 while：只要 _handlePostAgentRun() 返回 true（需要重试、溢出恢复、或有排队消息），就再调 agent.continue()。之后还会跑 agent_before_settle 边界；扩展若要求继续，同样 continue()。

packages/coding-agent/src/core/agent-session.ts ts
  • L1901agent.prompt() 自己会一直跑到 agent_end；这里的循环是产品级重试/恢复，不是 agent loop 的替代。
  • L1904agent.continue() 从现有 transcript 继续，不新增用户消息。它依赖尾部是 user/toolResult，而不是 assistant。
  • L1908agent_before_settle 是“这次真的没事了”之前最后一个可插入工作的边界；它也能要求继续。
  • L1910-1916finally 保证无论成功、失败、取消，都清理临时状态并发出 agent_settled。空闲等待者靠这个信号被唤醒。

4.4投影：让 agent 看到的 ≠ 磁盘上存的

这是整个 harness 最重要的设计之一。磁盘上的 JSONL 是只追加的事实；模型看到的是经过投影的视图。压缩、分支、上下文编辑、隐藏工具，都只改变投影，不删原始记录。

_installAgentRequestProjection() 在每次请求前做替换：

packages/coding-agent/src/core/agent-session.ts ts
  • L793每次请求都重建投影。没有“上次投影缓存”，避免状态不一致；投影本身是线性扫描，成本可接受。
  • L796模型可见消息来自会话投影，而不是 agent.state.messages 的原始累积。
  • L797-798工具是两套东西：消息里的 system 声明“模型可以调用什么”；context.tools 是“运行时能执行什么”。投影负责让两者一致。
  • L800包装链：先让内层钩子（可能是别的子系统）改写，再以自己的上下文为准。返回值里的 projection 供后续压缩判断复用。

为什么不让 agent 直接持有“当前历史”？因为一旦直接改数组，很多不变量会破：工具调用与结果必须成对、assistant 的 toolCall id 必须唯一、压缩边界必须原子。投影把所有这些规则集中在一个纯函数里（buildSessionProjection），agent 只消费结果。

心智模型

把 JSONL 想成 git 的对象库，把投影想成工作区。压缩是“新的提交”，不是“删除文件”；上下文编辑是“覆盖某一行”，原始行仍在。这个类比在第五章会展开。

4.5系统提示：结构化区块 + 差量补丁

pi 不把系统提示当一个大字符串存。它被拆成有名字的 section（身份、规则、工具说明、项目上下文、技能等），每次只把变化的 section写成一条 system 消息：

SystemMessage {
  role: "system",
  content: "",
  sections: {
    tools: "…",          // 只包含发生变化的 section
    guidelines: "…"
  },
  toolsAdded: [...],
  toolsRemoved: [...]
}

_preparePromptAndToolLoadout() 负责计算差量。它同时处理工具列表与提示文本：工具被隐藏时，对应的说明也必须消失，否则模型会看到“不存在的工具”。

packages/coding-agent/src/core/agent-session.ts ts
  • L1761先应用工具负载（allowlist、exclude、隐藏、MCP 连接状态），再取名字。顺序错了会把不该出现的工具写进提示。
  • L1764hiddenTools 与声明保持一致，避免“提示里有、请求里没有”。
  • L1765-1768与当前系统消息做 diff；没有变化就返回 undefined，不产生空补丁。这让连续请求的 transcript 保持干净。
  • L1769content: "" 是有意的：结构化 section 才是事实来源，渲染发生在 provider 投影时。

对不支持“对话中途改系统提示”的模型，_installAgentForcedPromptProjection() 会把所有 system 消息折叠成请求开头的一条。这样同一份 transcript 可以服务两类 provider，不需要在存储层做分支。

4.6压缩与溢出恢复：三种情况，一次机会

_checkCompaction() 的注释列了三种自动压缩。把它们分开看，逻辑就清楚了：

情况触发是否重试为什么
1. 溢出 + 重试context overflow 错误，或可恢复的 length stop是，整轮一次响应没完成，压缩后重发请求可能成功。
2. 溢出 + 不重试响应成功，但 usage 超过窗口否结果已经拿到；continue() 无法从 assistant 尾部继续。
3. 阈值投影估算超过阈值否只是预防性整理，不改变已完成的轮次。

“一次机会”由 _overflowRecoveryAttempted 控制。失败后再次溢出会直接发出 compaction_end 错误，而不是无限循环。另一个容易忽略的细节：如果错误来自另一个模型（用户切到了更大窗口的模型），不会触发压缩，因为旧模型的限制不适用于新请求。

压缩发生在哪两个位置

  • 下一轮开始前：_installAgentNextTurnRefresh 调 _compactBeforeNextAssistantResponse，用当前模型与投影判断阈值。
  • 请求前：虚拟模型路由后，用实际路由到的模型再判断一次；若超阈值，重新投影并压缩。

压缩本身不改 JSONL 的旧条目，而是追加一条 compaction 条目，记录 summary、保留起点、压缩前 token 数。投影从这条条目开始重建上下文。

4.7重试：把失败响应“重放”一次

自动重试与压缩不同：它发生在 agent_end 之后，由 _handlePostAgentRun() 判断最后一条 assistant 是否是可重试错误。关键设计是 _failedResponse：

  • 失败的 assistant 消息不再留在投影上下文里（否则模型会看到自己上次的失败输出）。
  • 重试请求把这条消息作为 failed 传给模型路由，用于选择“重试”语义（例如同一模型、同一档位）。
  • 成功响应会重置 _retryAttempt，避免一个长会话里错误累积到上限。

重试之间有延迟（retryDelayMs），并通过 auto_retry_start / auto_retry_end 事件让 UI 显示倒计时。用户可以随时 abort，_retryAbortController 会取消等待。

错误也是需要清理的状态

如果失败响应带有工具调用，对应的 toolResult 也必须一起从投影中移除，否则会留下“孤儿结果”。_omitRecoveryAttempt() 用 context edit 把 assistant 与其工具结果成对隐藏——这是“追加式删除”的典型写法。

4.8工具权限与扩展钩子

AgentSession 不实现权限系统，但它提供了挂载点。构造函数把 agent 的两个钩子直接接到扩展：

  • beforeToolCall → tool_call 处理器，可返回 { block, reason, terminate }。
  • afterToolCall → tool_result 处理器，可替换 content/details/isError/usage，之后还会做图片归一化。

嵌套工具调用（工具通过 ctx.executeTool() 调另一个工具）也走同一套钩子，并带 parentToolCallId。这意味着权限检查无法被“套一层工具”绕过——这是安全设计上的重要细节。

但要注意 pi 的定位：它没有内置的沙箱或权限模型。默认情况下工具直接以当前用户身份执行；扩展运行在同一进程。安全性来自你安装的扩展、运行的容器、以及 beforeToolCall 钩子。（详见第七章。）

4.9评价：薄循环，厚边界

AgentSession 超过 4000 行，但它的大部分代码不是“算法”，而是边界处理：压缩与重试的竞态、扩展钩子的顺序、取消与空闲的信号、投影与持久化的一致性。这恰好是产品级 harness 与教学 demo 的差别。

它的可读性依赖于一条纪律：所有对模型可见状态的修改，最终都汇聚到投影；所有对生命周期的干预，都通过少数几个钩子。破坏这条纪律的补丁会让系统迅速变得难以推理。读这部分源码时，建议始终问两个问题：

  1. 这个操作改的是事实（JSONL）还是视图（投影）？
  2. 它发生在 agent loop 的哪个钩子里？如果发生在事件回调里，是否可能与下一轮请求竞态？

读完本章，你应该能回答

  • agent.state.messages 与 sessionManager.buildSessionProjection().messages 为什么可能不同？
  • 系统提示为什么要按 section 做 diff，而不是每次重发全文？
  • 溢出恢复为什么只允许一次？什么样的错误不触发压缩？
  • 扩展的 tool_call 钩子如何阻断一次工具调用？阻断结果会进入模型上下文吗？
