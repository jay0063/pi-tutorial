pi 的会话是一个 JSONL 树：每条记录有 id 和 parentId，一个 leafId 指针决定当前分支。压缩、编辑、分支摘要都不删除旧行，而是追加新事实，再通过投影决定模型看见什么。

5.1为什么不用数据库

一个会话文件就是一个追加写的 JSONL。这个选择带来几个直接好处：

  • 可恢复：进程崩溃最多丢最后一行；前面的内容仍可读。
  • 可审计：模型看到的、用户改过的、压缩掉的，全都有原始记录。
  • 可分支：回到任意历史点继续，不需要复制整个会话。
  • 易分享/导出：纯文本，不依赖数据库版本。

代价是：查询要线性扫描；文件会越来越大；并发写需要外部约束。pi 接受这些代价，因为单机会话的规模有限，而“历史不可变”带来的调试价值更高。

5.2文件格式：一行一个事实

文件第一行是 header，之后每行是一个 entry。header 没有 id/parentId，不属于树：

{"type":"session","version":3,"id":"uuid","timestamp":"…","cwd":"/path/to/project"}
{"type":"message","id":"a0b1c2d3","parentId":null,"timestamp":"…","message":{...}}
{"type":"message","id":"d4e5f6a7","parentId":"a0b1c2d3","timestamp":"…","message":{...}}
{"type":"model_change","id":"…","parentId":"d4e5f6a7","timestamp":"…","provider":"openai","modelId":"gpt-5"}
{"type":"compaction","id":"…","parentId":"…","summary":"…","firstKeptEntryId":"…","tokensBefore":50000}
{"type":"context_edit","id":"…","parentId":"…","targetId":"a0b1c2d3","replacement":null}

entry 的完整联合类型有十几种：消息、模型切换、思考档位切换、usage、压缩、分支摘要、自定义数据、自定义消息、上下文编辑、标签、会话信息。关键是只有一部分参与模型上下文：

entry进入上下文？作用
message是system / user / assistant / toolResult 消息。
custom_message是扩展注入的内容，投影成 user 消息。
compaction是（作为摘要）替代被压缩的前缀；携带系统提示检查点。
branch_summary是（作为摘要）切分支时保留被放弃路径的要点。
context_edit间接改写或隐藏某个目标 entry 的贡献。
custom否扩展私有状态，重载时扫描恢复。
usage / label / session_info否计费、书签、显示名。

5.3当前分支 = 从 leaf 走到 root

SessionManager 只维护一个可变指针 leafId。所谓“当前会话”就是从 leaf 沿 parentId 向上直到根，再反转。复杂度 O(深度)，不需要遍历整棵树。

  • L403没有显式 leaf 时，回退到文件最后一个 entry。这是加载旧会话/损坏指针时的兜底。
  • L412只沿 parentId 走；遇到断链（父节点不存在）就停。加载时孤儿会被当作根处理。
  • L414反转得到从旧到新的顺序。之后所有投影逻辑都假设这个顺序。

5.4投影：把树压成一条时间线

模型只接受线性消息数组。投影要做三件事：取当前路径、找到最新压缩边界、应用上下文编辑。先看压缩如何裁剪路径：

packages/coding-agent/src/core/session-manager.ts ts
  • L481先取完整路径。压缩只影响模型视图，不改变树的形状。
  • L484-488沿路径找最新的 compaction。循环不 break，后面的覆盖前面的。
  • L501-503输出以 compaction 自身开头：它的 summary 会变成一条压缩摘要消息。
  • L504-510从路径头开始，直到遇到 firstKeptEntryId 才开始保留；之前的都被摘要替代。
  • L509保留区间里的 system 消息被跳过：压缩条目携带了 systemMessage 检查点，旧提示不应重复。
  • L511压缩条目之后的 entry 全部保留（包括后续对话）。
压缩预算模拟 200k window
阈值 = 上下文窗口 − 预留输出（默认 16k）。压缩保留最近约 20k tokens 的消息，其余变成摘要。原始记录仍在文件里。

5.5上下文编辑与分支摘要

有时你不想压缩，只想“让某条消息不再出现在模型上下文里”，或者“把它的内容换掉”。context_edit 就是为此设计的：

{"type":"context_edit","id":"…","parentId":"…",
 "targetId":"a0b1c2d3",
 "replacement": null}                          // 完全隐藏
{"type":"context_edit","id":"…","parentId":"…",
 "targetId":"a0b1c2d3",
 "replacement":{"content":[{"type":"text","text":"…"}]}}  // 只换内容

投影时，所有 context_edit 先按 targetId 建索引，再在生成消息时应用。只允许替换 content，不能改角色、toolCallId、时间戳等元数据——这保证工具调用与结果仍然配对，也保证审计信息不被篡改。

replacement: null 是“从模型上下文里省略”，不是“删除记录”。重试恢复正是用它把失败尝试及其工具结果成对隐藏，避免孤儿 toolResult 让下一次请求报错。

分支摘要

在会话树里跳到一个旧节点继续，原路径的上下文会从模型视野里消失。若那段工作很重要，可以在切分支时生成 branch_summary：它记录“从哪个节点来（fromId）”和摘要文本，投影成一条消息，让新分支知道旧分支做过什么。

这与压缩的差别是：压缩替换当前路径的前缀；分支摘要保留另一条路径的要点。两者可以同时存在。

5.7落盘、加载与迁移

写入是同步的：appendFileSync(sessionFile, JSON.stringify(entry) + "\n")。对单进程 CLI 来说，这比异步队列简单可靠；代价是每次写会阻塞事件循环几毫秒。pi 的应对是只在消息边界写，不按 token 写。

  • 加载：按 1MB 缓冲区流式读取，逐行 JSON.parse；坏行跳过而不是整个文件失败。
  • 迁移：v1 的线性会话自动转成树；v2 到 v3 主要是角色重命名（hookMessage → custom）。
  • 压缩时：先记录 systemMessage 检查点（当前系统提示的完整快照），这样即使压缩跨过提示变更点，重放也能得到正确提示。
  • 并发：同一条会话不应被两个进程同时写。pi 没有文件锁；它假设一个会话同时只有一个活跃的 harness。
“不可变”不等于“不可改”

文件是追加写的，但你可以用 context_edit 改模型视图，用 label 改显示，用 session_info 改名。真正的原始消息内容永远保留——除非你手动编辑文件。做取证/审计时，应以原始 entry 为准，而不是投影。

5.8设计评价

这套模型的优雅之处在于把“历史”与“视图”彻底分开：

  • 分支不需要复制文件，压缩不需要重写文件，编辑不需要破坏配对。
  • 任何时刻都可以重建模型上下文：给定文件与 leafId，投影是纯函数。
  • 调试时可以对照“模型看到了什么”和“实际发生了什么”，两者都有据可查。

代价是概念负担：读源码时必须同时跟踪 entry 树、leaf 指针、投影、压缩边界、context edit 五层。尤其 buildContextEntries 里“保留区间中的 system 消息被跳过”这种规则，不读注释很难推断。pi 用文档和类型把这些规则显式化，这是它作为教学样本的另一个优点。
