12.2第一次会话：观察而不是背命令

给一个具体、可验证的任务，例如：

读一下 src/server.ts，给 /healthz 加一个健康检查接口，
并补一个测试。改完运行测试。

你会看到 pi 的典型工作流：

  1. 先读文件/搜索，而不是直接改；
  2. 调用 edit/write，工具结果回到上下文；
  3. 运行测试，失败则继续修；
  4. 最后给一个简短总结。

常用交互：

操作作用
/model · Ctrl+L切换模型与思考档位。
/compact把历史压缩成摘要，释放上下文。
/tree · /fork · /clone查看/切换分支，探索另一条路线而不丢失原工作。
! 开头直接运行终端命令，不经过模型。
Ctrl-C中止当前运行；会话保留。
实验：故意让它失败

让它改一个不存在的文件，观察工具错误如何以 isError 结果回到模型，以及模型如何自己纠正路径。这比读十遍 loop 代码更能理解“工具错误是上下文的一部分”。

12.3写第一个扩展：一个自定义工具

扩展是一个导出默认工厂的 TypeScript 模块。下面这个例子完整、可运行，来自仓库的 examples/extensions/hello.ts：

packages/coding-agent/examples/extensions/hello.ts ts
  • L5-6TypeBox 提供运行时 schema；defineTool 保留参数类型推断，避免 params 退化成 unknown。
  • L8-14name 是模型看到的函数名；description 是模型决定是否调用的主要依据，写清楚“什么时候用”比写实现细节更重要。
  • L16-21content 是给模型看的文本；details 是给 UI/扩展用的结构化数据，不进入模型上下文。分开两者可以避免把调试信息塞进 token。
  • L24-26工厂在加载时执行一次；registerTool 必须在这里调用。不要在工厂里启动进程或定时器（见 12.8）。

把它放到用户扩展目录，或直接用命令行加载：

# 方式一：放到 ~/.pi/agent/extensions/hello.ts，重启 pi
# 方式二：开发时直接指定
pi --extension ./hello.ts

然后对 pi 说“用 hello 工具跟 Ada 打个招呼”。模型会调用 hello({ name: "Ada" })，你会在终端看到工具卡片和返回文本。

加一条安全规则

工具不一定要“做事”，也可以“阻止做事”。在扩展里监听 tool_call，检查参数并返回 block：

pi.on("tool_call", (event, ctx) => {
  if (event.toolName !== "bash") return;
  const cmd = String(event.input.command ?? "");
  if (/\brm\s+-rf\b/.test(cmd)) {
    return { block: true, reason: "rm -rf is not allowed in this project" };
  }
});

这条规则会失败关闭：只要扩展明确 block，工具就不会执行。注意 tool_call 处理器抛异常也会阻止工具（第 07 章讲过这个例外），所以规则本身要尽量简单、可预测。

12.4用 SDK 把 pi 嵌进你的程序

如果你的宿主是 Node 进程，不需要解析终端输出，直接用 createAgentSession()。最小示例：

packages/coding-agent/examples/sdk/01-minimal.ts ts
  • L10默认使用当前目录、已发现的扩展/技能/工具、已保存的设置与凭证。想隔离就传 SessionManager.inMemory() 与显式 cwd。
  • L13-17先订阅再 prompt，否则会漏掉开头的流式事件。只处理 text_delta；工具调用、压缩、重试各有事件类型。
  • L19prompt() 在整次 run 结束后才 resolve，包括自动重试。它不是“发出去就返回”。
  • L25dispose() 中止活动任务、注销扩展、断开监听。忘掉它会泄漏进程资源。

几个常用配置：

const { session } = await createAgentSession({
  cwd: "/path/to/project",
  tools: ["read", "grep", "find", "ls"],       // 只读模式
  sessionManager: SessionManager.inMemory(),   // 不落盘
  thinkingLevel: "high",
});

如果宿主需要“运行结束后绝不再自动继续”的信号，用 agent_settled，而不是 agent_end。后者只表示一次低层 run 结束，之后还可能因重试、压缩、排队消息继续。

12.5五天读源码路线

不要从 coding-agent/src 的第一行开始读。按依赖倒序，每天一个主题，每个主题配一个可验证的问题：

天读什么带着什么问题验证方式
1packages/ai/src/types.ts、utils/event-stream.ts、一个 provider 适配器一条流式响应如何变成事件？result() 与迭代器如何共存？写一个小脚本消费 EventStream，打印事件序列。
2packages/agent/src/loop.ts、types.ts内外两层循环各负责什么？并行工具结果如何保持顺序？在 prepareToolCall 里加日志，观察一次双工具调用。
3coding-agent/src/core/agent-session.ts六个钩子分别改变什么？prompt 从输入到请求经过哪些阶段？订阅事件，打印 turn_start/turn_end/agent_end/agent_settled 的顺序。
4session-manager.ts、messages.ts、compaction 相关文件树如何投影成上下文？压缩后保留区从哪开始？打开一个真实会话 JSONL，手算 buildContextEntries 的结果。
5packages/tui/src、coding-agent/src/modes一帧如何 diff？五种接口模式如何复用同一个 session？用 --mode json 跑同一任务，对比交互模式的事件。

每天结束前，写下三个“为什么这样设计”的答案。读不懂的地方，先看测试：packages/*/test 往往比实现更能说明契约。

12.6三个练习

练习 1：成本哨兵

写一个扩展，在每轮结束后读取本次运行的 usage，累计成本；超过阈值时用 ctx.ui.notify() 提醒，并在状态栏显示当前会话总花费。提示：成本字段已经在 Usage.cost 里算好，不要自己乘单价。

练习 2：路径守卫

监听 tool_call，对 edit/write 的参数做 realpath 解析，阻止写到工作区之外。注意符号链接与 ..；比较时统一大小写（Windows）。这个练习会让你真正理解“工具参数不可信”。

练习 3：上下文可视化

订阅 turn_start 或上下文相关事件，按类别估算当前上下文体量：系统提示、工具结果、用户消息、assistant 消息。不需要精确 tokenizer，用字符数分桶即可；目标是看清“谁在吃窗口”。

调试扩展

扩展与 pi 同进程，console.log 可能被 TUI 覆盖。优先用 ctx.ui.notify() 或写文件日志；也可以用 --mode json 跑，让标准输出干净一些。

12.7常见坑

现象原因处理
扩展改了但没生效jiti 禁用了模块缓存，但工厂只在加载时执行重启 pi，或用扩展命令触发 reload；不要依赖模块级状态跨 reload。
工具调用参数是 unknown直接传对象字面量，上下文类型放宽了用 defineTool() 包一层，保留 schema 推断。
模型看不到新工具工具注册了但未激活检查 setActiveTools/默认工具设置；工具声明在下次请求前才发给模型。
压缩后“忘了”之前的决定摘要丢失细节，或切点选错把关键约束写进项目上下文/系统提示；必要时用分支回到压缩前。
agent_end 后还有输出重试、压缩重试或排队消息又启动了一次 run用 agent_settled 判断真正结束。
扩展能读我的凭证同进程、同权限只安装可信扩展；需要隔离就用容器（见第 11 章）。
Windows 上路径/命令异常bash 工具与 PowerShell 工具语义不同优先用 read/edit/grep 等跨平台工具；明确指定 shell。

12.9结语：把 agent 当成分布式系统

回头看，pi 的每一层都在回答同一个问题：当外部依赖又慢、又贵、又会出错时，如何让系统仍然可理解、可恢复、可扩展？

  • pi-ai：把不可控的 provider 关进适配器；
  • agent-core：用明确的事件与 turn 边界描述控制流；
  • AgentSession：用组合与钩子把策略和机制分开；
  • 会话树：用不可变日志换可审计与可分支；
  • 扩展：把定制推到进程边界，而不是塞进核心；
  • TUI：承认终端是流，只改该改的行。

这些选择不完美，但彼此一致。理解它们之后，你不需要记住每个函数——你可以在需要时找到正确的那一层，并且知道改动会波及哪里。

最后检查

  • 你能在不看源码的情况下画出 prompt → turn → tool → compaction 的事件顺序吗？
  • 如果让你给 pi 加一个“审批危险命令”的功能，你会放在扩展、session 还是 loop？为什么？
  • 如果上下文总是溢出，你会先改工具结果、压缩策略，还是系统提示？依据是什么？
  • 你能解释为什么 agent_end 不等于“任务结束”吗？
