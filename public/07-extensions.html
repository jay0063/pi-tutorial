pi 不内置权限系统，也不写死工作流。它提供一层进程内扩展：TypeScript 模块通过 ExtensionAPI 注册工具、命令与事件处理器，直接看到提示、工具调用与会话。这给了极大的自由度，也意味着扩展就是你的代码——同等的权限，同等的风险。

阅读约 30 分钟 关键文件 4 个 安全警告必读
信任模型：没有沙箱

扩展运行在 pi 进程内，拥有与 pi 相同的操作系统权限。它能读取凭据、修改文件、发网络请求，也能看到完整会话。只加载你信任的来源。项目级扩展/包只有在 project_trust 通过后才会加载，但“信任”是一次性的人类决定，不是技术隔离。

7.1扩展、技能、包、MCP：别混为一谈

pi 的“可扩展性”由四个不同层次组成，解决的问题不同：

机制是什么能做什么不能做什么
Skill带 frontmatter 的 SKILL.md + 资源文件按需加载的指令、脚本、参考文档不能注册工具或拦截事件
Extension进程内 TypeScript 模块工具、命令、事件钩子、provider、UI不能跨进程隔离
Pi packagenpm/git/本地目录打包分发 extensions/skills/prompts/themes本身不是运行时机制
MCP server外部进程或 HTTP 服务提供工具与资源，跨语言能力受协议限制，需连接管理

选择原则：需要执行代码 → 扩展；只需要指令 → 技能；需要跨语言/隔离 → MCP；需要分发 → package。

7.2加载：jiti 直接跑 TypeScript

扩展不需要预编译。pi 用 jiti 在运行时转译 TypeScript，并复用宿主模块与 tsconfig 路径。工厂函数可以是同步或异步的；异步工厂会被等待，因此可以在启动时拉取配置或注册 provider。

packages/coding-agent/src/core/extensions/loader.ts ts

  • L580resolutionOptions 区分三种运行形态：编译后的二进制（虚拟模块）、源码运行（tsconfig paths）、普通 Node 构建（dist alias）。
  • L584{ default: true } 只取默认导出；扩展必须 export default function (pi) {…}。

7.3生命周期：一次 run 的钩子顺序

扩展事件不是一堆同质的回调。它们分布在不同的时间尺度上，从“输入还没变成消息”到“进程即将退出”。

会话生命周期是另一条线：project_trust → session_start →（切换/分叉时）session_before_switch / session_before_fork → session_shutdown。重载会让旧运行时失效；await ctx.reload() 之后的代码仍属于旧运行时，不能复用它的会话状态。

7.4事件组合模型：五种语义

事件类型很多，但组合方式只有五种。理解这个分类，比背事件名有用：

模式行为典型事件
通知返回值忽略，只观察agent_start、agent_settled、provider_stream_event
就地修改后续处理器看到前者的修改before_provider_headers、tool_call.input
链式变换后一个收到前一个的返回值input、context、message_end、tool_result
闸门返回 handled/block/cancel 终止正常路径tool_call、user_bash、session_before_*
可操作边界看到已提议的 entries 与 continue 决定，可追加turn_end、agent_before_settle

处理器按扩展加载与注册顺序运行；pi.on() 返回取消订阅函数，且不影响正在进行的派发（派发用的是快照）。

错误处理并不统一

大多数事件里，某个处理器抛错会被捕获、报告给 emitError，然后继续下一个处理器。但 tool_call 是例外：emitToolCall() 不捕获，错误会冒泡到 agent 的工具准备阶段，被转成一条错误 toolResult，从而阻止该工具执行。这是有意为之——权限钩子失败时应当 fail closed（拒绝），而不是放行。

packages/coding-agent/src/core/extensions/runner.ts ts
  • L1251没有 try/catch。任何处理器抛错都会让整次工具调用失败——这是安全边界上的刻意选择。
  • L1257-1261第一个 block: true 立即短路。之后的处理器不会再看到这个调用。
  • L1266若没有 block，返回最后一个非空结果（通常带 terminate 之类的提示）。

7.5ExtensionAPI：能力清单

工厂函数拿到的 pi 对象是扩展的全部入口。常用的能力可以分成六类：

注册能力

registerTool、registerCommand、registerShortcut、registerFlag、registerProvider、registerMcpServer、registerVirtualModel。

监听事件

pi.on(event, handler)。返回取消函数。处理器按注册顺序运行。

消息与会话

sendUserMessage、sendMessage、appendEntry、setActiveTools、模型/思考档位控制。

工具编排

ctx.executeTool() 走完整校验与钩子；ctx.tools 列出可调用工具。

终端 UI

ctx.ui.notify、confirm、自定义渲染器、状态行；仅在交互模式可用。

扩展间通信

pi.events 提供轻量事件总线；共享状态应通过 session entry 持久化。

7.6工具暴露：不是所有工具都直接给模型

扩展可以注册很多工具，但并非都要出现在系统提示里。pi 用 exposure 控制“模型如何到达这个工具”：

exposure声明给模型可被其他工具调用典型用途
direct（默认）激活时是激活时是普通工具，如 read/write。
model-only激活时是否需要用户确认、编排其他工具的工具。
codemode仅显式激活始终可被脚本批量调用，不占系统提示。
deferred仅显式激活始终可由 tool_search 发现后激活。
hidden否否注册但不可达；用于“撤回”工具。

这解决了一个真实问题：工具太多会撑爆系统提示，也会让模型选择困难。pi 的策略是“按需暴露”：默认只给核心工具，其余通过 codemode 或 tool_search 间接使用。

7.7安全：自由与责任的边界

pi 的安全模型可以概括为三句话：

  1. 扩展是代码，不是配置。它能做 pi 能做的一切，包括读 ~/.ssh、发请求、改会话文件。
  2. 项目资源需要信任。项目级扩展与包在 project_trust 之后才加载；个人扩展与显式 --extension 不经过这道门。
  3. 没有内置沙箱。要隔离，用容器、虚拟机、受限用户，或只加载审计过的扩展。

官方文档甚至建议：把扩展当作“你和你的团队写的代码”来审查；第三方 package 要先看源码；不要让不可信仓库的 .pi/ 配置自动生效。这不是过度谨慎——一个 tool_call 钩子就能把 rm -rf 包装成“安全”的 clean 工具。

容器化

pi 提供 containerization.md，建议在容器里运行并只挂载工作目录。这是目前最实际的隔离手段：即使扩展或模型被诱导执行危险命令，破坏也被限制在挂载范围内。

7.8设计评价

这是一套“平台化”的扩展模型：核心保持小，能力通过进程内钩子生长。优点是表达力极强——你几乎可以改变任何行为，而不必 fork；缺点是没有稳定的安全边界，且钩子顺序、错误语义、重载生命周期都需要学习。

与 MCP 相比，扩展更强大但更危险；与插件式沙箱相比，扩展更灵活但更难审计。pi 的选择与它的定位一致：面向愿意读源码、自己承担责任的开发者。读这套代码时，值得把“如果这是我写的权限钩子，它会在哪些情况下失效”作为练习。
