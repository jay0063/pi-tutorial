工具与运行接口
Chapter 06 · tools & surfaces

工具是函数，
也是一份给模型的合同

在 pi 里，工具不是“能力插件”，而是三样东西的组合：给模型看的 schema 与说明、给运行时执行的函数、给 UI 的渲染器。这一章从 AgentTool 契约读到内置工具的实现细节，再看同一内核如何暴露成五种运行接口。

阅读约 30 分钟 关键文件 6 个 工具链 + 接口矩阵

6.1AgentTool：最小执行契约

AgentTool 只比“带 schema 的函数”多几个可选字段。它刻意保持小，因为这是扩展作者与内核之间的稳定边界。

packages/agent/src/types.ts ts
  • L466继承自 Tool，后者提供 name、description、parameters（TypeBox schema）。这四个字段就是模型看到的合同。
  • L473prepareArguments 在 schema 校验之前运行，用来兼容模型发来的畸形参数（JSON 字符串、别名、缺省包装）。
  • L483execute 拿到的是已校验、已规范化的参数，不需要再防御类型。
  • L486signal 用于协作式取消；工具应把它传给子进程/网络请求，而不是忽略。
  • L490replay 是给持久化执行/恢复用的：有副作用且结果未知的工具应标 "never"，避免自动重放。
  • L498executionMode: "sequential" 会让整个批次降级为串行，用于有共享状态的工具。

产品层还有更丰富的 ToolDefinition：它多了 promptSnippet、promptGuidelines、renderCall、renderResult、exposure、constrainedSampling 等。内核只认 AgentTool；这些产品字段在装配时被消费——提示进入系统提示，渲染器进入 TUI，schema 进入 provider 请求。

6.2工具结果：一份结果，三种读者

AgentToolResult 的字段分工，是 pi 工具设计里最值得借鉴的部分：

字段读者是否进上下文用途
content模型是文本/图片。应当简洁，只包含模型决策所需信息。
detailsUI / 扩展 / 日志否完整结构，例如 diff、截断信息、文件列表。
structuredContent程序调用者否匹配 outputSchema 的机器可读结果，codemode 直接消费。
usage计费否工具内部调用模型的花费（如子 agent）。
isError模型 / 循环是（标记）让失败成为可重试的上下文，而不是异常。
terminate循环否整批一致时提前结束自动续跑。
实践建议

写工具时先问：模型需要看到多少？ 例如 grep 的 details 可以包含全部命中，content 只给前 N 条加一句“还有 237 条，可用 offset 继续”。这比把几万行塞进上下文更能让模型做对下一步。

6.3八个内置工具的设计取舍

pi 的内置工具刻意保持“Unix 小工具”风格，而不是提供一个万能 computer 工具。默认集合是：read、bash、edit、write、grep、find、ls，Windows 上还有 powershell。

工具关键设计为什么
readoffset/limit 分页；图片自动缩放；默认最多 2000 行 / 50KB大文件不能一次塞满上下文；图片要按模型限制缩放。
edit多个 oldText/newText，全部基于原始文件匹配；不重叠一次调用完成多处修改，减少往返；避免增量匹配的歧义。
write整文件覆盖；自动建父目录；走文件队列适合新建或完整重写，不适合局部修改。
bash合并 stdout/stderr；可流式更新；尾部截断；完整输出存临时文件命令输出通常“最后几行最重要”；截断后仍能给出完整路径。
grep按行截断（默认 500 字符）；结果分页避免单行超长（压缩后的 JS）撑爆上下文。
find按 glob/名称查找；限制结果数大仓库里“找文件”本身可能产生海量输出。
ls目录列表；隐藏文件可选比 bash 更安全、输出更稳定。
powershellWindows 专用，独立 shell 配置不把平台差异塞进 bash 工具。

read：分页而不是“读整个文件”

read 的 schema 只有三个字段，却决定了模型能否在大仓库里工作：

const readSchema = Type.Object({
  path:   Type.String({ description: "Path to the file to read (relative or absolute)" }),
  offset: Type.Optional(Type.Number({ description: "Line number to start reading from (1-indexed)" })),
  limit:  Type.Optional(Type.Number({ description: "Maximum number of lines to read" })),
});

截断策略是“头截断”：保留前 2000 行或前 50KB，谁先到算谁。返回的 details.truncation 包含总行数、总字节、命中哪个限制，模型可以据此决定是否用 offset 继续读。图片走另一条路径：检测 MIME、按模型输入限制缩放、返回 image block；若模型不支持图片，则用一句提示替代。

edit：基于原文的多点替换

编辑工具不接受行号，也不接受正则，而是要求 oldText 在文件中唯一且精确匹配。这看起来苛刻，但消除了几类常见错误：行号漂移、缩进不一致、正则误匹配。多个 edit 都在原始内容上匹配，因此调用者必须保证它们不重叠。

这个约束也把“如何改”推回给模型：它必须先读文件、复制精确文本。对 agent 来说，这比“猜行号”更可靠。

bash：尾部截断 + 完整输出落盘

命令输出与文件读取相反：通常最后几行才是关键（错误、测试摘要）。所以 bash 用 truncateTail，保留最后 2000 行 / 50KB，并在内容末尾附上：

[Showing lines 812-2811 of 2811 (50.0KB limit). Full output: /tmp/pi-bash-….log]

模型因此知道“输出被截断了”，也能在需要时用 read 打开完整文件。timeout 是可选的，且没有默认值——长命令（构建、测试）不应该被一个拍脑袋的默认值杀掉。

6.4并行工具下的文件竞态

agent loop 默认并行执行工具。如果同一批里有 edit a.ts 和 write a.ts，天真的实现会互相覆盖。pi 用按真实路径串行化的队列解决，而不是把 edit/write 标记为全局串行：

packages/coding-agent/src/core/tools/file-mutation-queue.ts ts
  • L33registrationQueue 把“注册到哪个队列”这个动作本身串行化，避免两个调用同时创建同一个文件的队列。
  • L34getMutationQueueKey() 优先用 realpath，这样符号链接和真实路径会落到同一个队列。ENOENT 时退回解析后的路径（文件还不存在）。
  • L38-41经典的 Promise 链：当前任务完成后才 releaseNext()，后续任务在 currentQueue 上等待。
  • L52不同文件的队列互不影响，因此并行度保留；只有同一文件被串行化。
  • L57finally 保证异常也会释放队列；最后一个等待者清理 Map，避免内存泄漏。

这个队列只保护“经由 pi 工具发起的写入”。外部进程（例如用户同时跑 npm run format）仍可能竞争。要更强的一致性，需要文件锁或版本控制层的冲突检测——pi 把这个问题留给环境，而不是在内核里做分布式锁。

6.5五种接口，一个内核

pi 的产品形态不是“一个 CLI”，而是同一 AgentSession 的多个投影。输入输出的差异被限制在 mode 层，内核不感知终端、JSON 管道或 RPC 客户端。

接口传输生命周期适用
interactive终端（TUI）长驻，多轮人类日常使用；需要交互确认、图像、快捷键。
printstdout 文本一次调用脚本、CI；--print 或非 TTY 自动选择。
jsonJSONL一次调用结构化消费：先 header，再 session events。
rpcJSONL 双向长驻子进程IDE、其他语言、需要进程隔离的宿主。
SDK进程内 TypeScript宿主控制Node/Bun 应用嵌入；直接操作 session 与事件。

JSON 与 RPC 的区别不只是“有没有 header”

JSON 模式是单向事件流：进程启动、执行给定 prompt、输出事件、退出。RPC 模式是双向协议：stdin 发 command，stdout 收 response 与 event，进程长期存活，客户端可以随时 prompt、get_state、set_model、abort。

两者共享同一套事件形状，但生命周期语义不同。最容易踩的坑是把 agent_end 当成“彻底结束”：它只表示一次低层 run 结束，之后还可能有自动重试、压缩恢复、steering 或 follow-up。真正表示“不会自动继续”的是 agent_settled。

packages/coding-agent/src/main.ts ts
  • L112显式的 --mode 优先，其次是 --print，最后根据 TTY 自动判断。管道输入/输出默认非交互，这让 echo ... | pi 自然工作。
  • L118“任一端不是 TTY”就进入 print。CI 里不需要额外 flag，也不会尝试启动 TUI。

6.6设计评价

这套工具层的优点是边界清晰：schema、执行、结果、渲染、提示贡献分别有位置；内核只依赖最小接口。新增一个工具不需要改循环，也不需要改 provider。

但它也把不少责任推给工具作者：

  • 你必须自己想清楚 content 与 details 的分工，否则要么上下文爆炸，要么 UI 信息不足。
  • 你必须遵守 signal 与 onUpdate 的约定，否则取消不生效、流式输出卡顿。
  • 文件类工具必须使用提供的队列，否则并行批次里会出现丢失更新。
  • 工具描述与 promptGuidelines 会直接影响模型行为；写得含糊，模型就会误用。

从教学角度看，内置工具是很好的“如何为模型设计 API”的样本：短描述、强约束、可恢复错误、明确的输出上限。这些原则比具体实现更值得带走。
