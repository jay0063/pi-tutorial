pi 不是一个“大而全”的 agent 框架。它把能力压到四个清晰的平面里：协议、运行时、harness、交互外壳。理解这四个平面的边界，后面每一处源码都会变得可预测。

1.1pi 的定位：一个“可改造”的 harness

README 的第一句话是：“Pi is a minimal, extensible agent harness that you can make your own.” 关键词不是 “agent”，而是 harness。模型负责推理，harness 负责让推理在真实世界里产生副作用：读文件、跑命令、改代码、保存会话、在终端里显示进度。

一个 coding agent 产品通常要回答五类问题：

问题pi 的回答落在哪一层
不同厂商的 API 怎么统一？把所有差异收敛到 Model + Message + 事件流pi-ai
模型要调工具，循环怎么停？一个双层 loop + 可插拔的 finishTurn / steeringpi-agent-core
会话、上下文、压缩怎么管？JSONL 树 + 投影（projection）+ 摘要条目coding-agent
怎么让用户改造行为？扩展、技能、提示模板、Pi packagescoding-agent
终端界面怎么不闪烁？自研布局 + 行级差分渲染pi-tui

它也明确不提供一些东西：没有内置的沙箱权限系统，没有 sub-agents，没有 plan mode（至少默认不带）。这些不是遗漏，而是产品哲学：核心保持薄，策略交给扩展和外部容器。

安全边界要先讲清楚

pi 的工具以启动它的操作系统用户权限运行；扩展是加载进同一进程的 TypeScript 模块，能读凭据、改文件、发网络请求。需要强隔离时，官方建议用容器或 micro-VM（见 docs/containerization.md）。读源码时不要把“没有权限系统”误解为“有隐式沙箱”。

1.2七个包，一条向下的依赖链

仓库是一个 npm workspaces monorepo。真正支撑 CLI 的主干只有四个包：pi-ai → pi-agent-core → pi-coding-agent，外加独立演进的 pi-tui。其余包（chord、durable、mcp、env、codemode、telemetry、evals）围绕“可复用的 agent 基础设施”展开。

这条依赖方向是整个架构最重要的事实。它带来三个直接结果：

  • 可嵌入：pi-agent-core 不依赖终端、不依赖文件系统，只依赖 pi-ai 的类型与流函数，所以可以被 SDK、RPC 服务甚至云端 runtime 复用。
  • 可替换：provider 由 pi-ai 的 Provider 接口描述，新增模型厂商不需要改 agent loop。
  • 可测试：pi-agent-core 接受一个 streamFn，测试里可以替换成纯粹的脚本化流，不需要网络。

1.3三个平面：数据、控制、呈现

比起包依赖，更有用的是按“职责平面”去读。pi 的代码基本可以放进这三个抽屉：

DATA PLANE

消息与轨迹

Model、Message、AssistantMessageEvent、AgentEvent、JSONL 条目。它们定义“发生了什么”，以及“模型看到了什么”。

CONTROL PLANE

循环与决策

agent loop、tool execution、steering / follow-up 队列、finishTurn、compaction、retry。它们决定“下一步做什么”。

PRESENTATION

交互与渲染

四个 mode、TUI 组件、主题、扩展 UI 请求。它们只消费事件，不改变模型上下文。

把这三个平面分开看，你会发现 pi 的一个隐含原则：呈现层不拥有状态，控制层不拥有界面，数据层不拥有策略。 例如 TUI 只订阅 AgentSessionEvent；会话是否压缩由 harness 决定；而 pi-ai 完全不知道“重试”或“队列”的存在。

1.4一次 prompt 的完整生命周期

下面这条路径是理解整个仓库的主线。建议在 IDE 里打开对应文件，顺着箭头读一遍。

  1. 输入预处理：AgentSession.prompt() 先尝试扩展命令，再跑 input 钩子，展开 /skill: 与提示模板。流式过程中提交的消息会按 steer 或 followUp 入队。
  2. 启动 run：_startRun() 触发 before_agent_start，允许扩展替换系统提示、工具或上下文；然后构造 AgentContext 快照。
  3. 进入循环：runAgentLoop() 添加消息、发 agent_start / turn_start，然后进入 runLoop() 的双层结构。
  4. 投影与请求：prepareRequest 钩子把 agent.state.messages 换成 SessionManager.buildSessionProjection() 的结果——这是“模型实际看到的上下文”，可能已应用 compaction 与 context edit。
  5. 流式响应：streamAssistantResponse() 调 convertToLlm，把 AgentMessage[] 降级为 provider 可理解的 Message[]，然后交给 streamFn。provider 适配器把 SSE 事件翻译成统一的 AssistantMessageEvent。
  6. 工具执行：assistant 消息里的 toolCall 块被逐个准备、校验、执行、后处理，结果变成 toolResult 消息。
  7. 持久化：每个 message_end 都会触发 SessionManager.appendMessage()，以 id/parentId 挂到当前叶子上。
  8. 决定是否继续：还有工具调用、steering、follow-up，或 finishTurn 返回 continue，就进入下一 turn；否则 agent_end。
  9. 收尾与恢复：agent_end 之后仍可能有自动重试、溢出恢复、压缩重试；真正空闲由 agent_settled 表示。
一个容易混淆的点

agent_end 不是“彻底结束”。它只表示这一次低层 run 不再产生事件；harness 可能因重试、上下文溢出恢复或排队消息而启动新的 run。需要“真正空闲”时，用 agent_settled（SDK / 扩展语义）。

1.5核心循环长什么样

先看骨架。这里是 runLoop 的开头，注意“外层 while(true) + 内层 while(hasMoreToolCalls || pending)”的结构：

packages/agent/src/agent-loop.ts ts · 节选
  • L172纯函数式入口：不持有状态，所有可变态通过参数与回调进入。这让它可被 Agent 包装，也可被测试直接调用。
  • L187外层循环处理“agent 本来要停了，但队列里又来了 follow-up”的情况。它只在真正无事可做时退出。
  • L191内层循环处理工具调用与 steering。一次内层迭代 = 一次 assistant 请求 + 它触发的工具批次。
  • L195prepareNextTurn 是 harness 插入压缩、模型切换、提示更新的位置；它可能很慢，所以之后要再收一次 steering。

注意 runLoop 不直接调用模型，也不直接执行工具。它通过 streamFunction 和 AgentTool.execute 两个端口与外界交互。这就是依赖倒置：核心定义协议，上层提供实现。

1.6六个值得记住的架构决策

决策代码证据收益 / 代价
消息即协议，provider 只做翻译 pi-ai/src/types.ts 的 Message / AssistantMessageEvent 新增厂商成本低；代价是要处理各家语义差异（reasoning、缓存、工具 ID、图片）。
工具调用是消息内容，不是回调 ToolCall 块嵌在 AssistantMessage.content 天然可持久化、可重放、可并行；代价是参数流式解析必须容错。
会话是 append-only 的树 SessionManager 的 id/parentId + leafId 分支/回溯不需要复制文件；代价是每次请求都要做投影。
上下文由“投影”生成，而非直接改历史 buildSessionProjection() 压缩、编辑、恢复都不破坏原始记录；代价是多一层抽象。
扩展是进程内代码 ExtensionRunner + jiti 能力极强、开发体验好；代价是信任边界等于进程边界。
TUI 自己管理终端 pi-tui 的 TuiBase.doRender() 无 React/Ink 依赖，控制力强；代价是要自己处理宽度、ANSI、光标、图像。
