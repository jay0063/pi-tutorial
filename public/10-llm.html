写 agent 不要求你会训练模型，但必须理解它的计费单位、上下文边界、采样参数和工具协议。这一章从“一次 HTTP 请求”讲起，把 pi 里那些看似神秘的字段放回它们真实的位置。

10.1一次调用到底发生了什么

把 LLM API 想成一个纯函数：

response = model(messages, tools?, sampling?, stream?)

它不记得上一次调用。所谓“对话”，是你每次把完整历史重新发过去。服务端可能做前缀缓存，但语义上仍然是无状态的。一次请求包含：

  • messages：system / user / assistant / tool 角色，内容可以是文本、图片、工具调用、工具结果。
  • tools：一组 JSON Schema 描述的函数签名。模型不会执行它们，只会“请求调用”。
  • sampling：temperature、top_p、max_tokens 等，控制输出分布与长度。
  • stream：是否用 SSE 增量返回。coding agent 几乎总是开流式，否则首字延迟不可接受。

响应也不是“一段字符串”，而是一串内容块：

assistant message
├─ text block        "我先读一下 server.ts"
├─ thinking block    （推理模型可选，可能加密/不可见）
└─ tool_use block    { id, name: "read", input: { path: "src/server.ts" } }
stop_reason: "tool_use"

pi 的 AssistantMessage 就是把各家的这种结构归一化后的结果：content: (TextContent | ThinkingContent | ToolCall)[]，外加 usage、stopReason、errorMessage。provider 适配器的职责，就是在“厂商 JSON”和这组内部类型之间来回翻译。

为什么 agent 框架都有一层“消息归一化”

Anthropic 的工具结果放在 user 消息的 tool_result 块里；OpenAI 用独立的 role: "tool" 消息加 tool_call_id；Google 用 functionResponse part。如果核心循环直接拼厂商格式，换模型就要改循环。pi 的做法是：核心只认内部 Message，适配器负责投影。

10.2Token：计费与容量的共同单位

模型不按字符处理文本，而按 token。一个 token 大约对应：

  • 英文：约 4 个字符，或 0.75 个单词；
  • 中文：常见汉字约 1–2 个 token（取决于 tokenizer 与词表）；
  • 代码：缩进、标点、常见标识符往往各占一个 token，实际密度比英文更低；
  • 图片：按分辨率折算成视觉 token，可能上千。

关键结论：字符数不是可靠的预算单位。pi 的 faux provider 用一个粗暴的估算做模拟：

packages/ai/src/providers/faux.ts ts
  • L159-161只用于本地假 provider 的延迟/用量模拟，不是真实计费依据。真实 token 数由 provider 返回的 usage 决定。
  • 为什么是 /4英文文本的经验平均值。对中文、代码、JSON 会显著低估，所以不能拿它做压缩阈值判断。

pi 的 Usage 把账单拆得很细，因为它直接影响成本优化：

packages/ai/src/types.ts ts
  • L460-463普通输入、普通输出、缓存命中读、缓存写入分开计。它们的单价可能相差 10 倍以上。
  • L471reasoning 是 output 的子集，不是额外项。很多账单只按 output 计，思考 token 已经包含在内。
  • L485totalFromProvider 区分“厂商报的实账单”与“本地按价目表估算”。两者可能因折扣/阶梯价而不一致。

成本计算的实现值得一读，因为它处理了两件容易错的事——阶梯价与长缓存写入的倍率：

packages/ai/src/models.ts ts
  • L1237阶梯价按“总输入量”选档：缓存读与写也计入，因为它们同样占用模型输入。
  • L1241-1247遍历所有 tier，取满足条件的最高阈值，而不是遇到第一个就停。价目表可以乱序。
  • L12541 小时缓存写入按基础输入价 2 倍计；短缓存写入用 cacheWrite 单价。把 cacheWrite1h 从总量里拆出来，避免重复计费。
  • L1256单价单位是“每百万 token”，所以除以 1_000_000。这是最常见的 1000 倍错误来源。

10.3上下文窗口：输入 + 输出的总预算

contextWindow 不是“历史消息的长度”，而是本次请求的输入 token + 期望输出 token 的上限。pi 的 Model 把它和 maxTokens 分开：

packages/ai/src/types.ts ts
  • L861reasoning 标记是否支持思考；它决定 UI 是否显示 thinking 块、是否允许设置 thinking level。
  • L869contextWindow 是模型的总窗口，来自模型目录，不因请求而变。
  • L870maxTokens 是单次输出上限。真正可用于输入的上限约为 contextWindow - maxTokens。
  • L872模型的默认采样参数放在这里；单次请求可以覆盖。这样“模型推荐配置”与“调用方意图”分开。

为什么编码 agent 特别容易撞墙？因为上下文里不只有对话：

  • 系统提示：工具说明、行为准则、项目上下文，常见 5–15k token；
  • 工具 schema：每个工具的 JSON Schema，十几个工具就是几千 token；
  • 工具结果：读一个文件可能 2k token，跑一次测试可能 10k；
  • 历史轮次：每一轮都保留之前的全部内容，线性增长；
  • 输出预留：必须给模型留出回答空间，否则会被截断。

“lost in the middle” 是另一个约束：即使内容在窗口内，模型对开头和结尾的注意力也强于中段。所以 pi 把系统提示与当前任务放在两端，把大量工具结果放在中间，并用压缩把中段控制在可管理范围。

10.4采样参数：控制分布，不控制事实

参数作用agent 场景的建议
temperature缩放 logits，越低越确定工具调用/代码编辑用低值（0–0.3）；创意写作可高。
top_p nucleus sampling，只保留累计概率前 p 的 token通常与 temperature 二选一调整，不要同时大幅改。
top_k只保留概率最高的 k 个 token部分 provider 支持；对代码任务可收紧。
max_tokens输出长度硬上限必须小于窗口余量；太小会截断工具调用 JSON。
stop遇到指定序列停止agent 很少用；容易与代码内容冲突。
seed尽量可复现仅部分 provider 支持，不保证跨版本一致。

pi 把这些放进 SamplingParams，并允许按 thinking level 覆盖（samplingParamsByThinkingLevel）。原因是推理模型在不同思考档位下推荐的温度不同；把“模型推荐值”与“用户覆盖值”分层，比在调用处硬编码更可维护。

temperature = 0 不等于确定性

浮点运算、批处理顺序、GPU 非确定性都会让同一请求产生不同结果。它只是“尽量选高概率 token”。不要在此基础上构建“重放必得同一答案”的测试；要测行为，就断言结构或不变量。

10.5工具调用：模型只出“意图”，执行永远在你这边

工具调用不是 RPC。模型输出的是一个结构化请求：

{
  "type": "tool_use",
  "id": "toolu_01ABC",
  "name": "read",
  "input": { "path": "src/server.ts", "limit": 120 }
}

你的运行时负责：查工具 → 校验参数 → 执行 → 把结果作为一条新消息追加 → 再次请求模型。这个闭环就是 agent loop 的核心。几个容易踩的坑：

  • id 必须原样回传。并行调用时，结果靠 id 与请求配对；顺序错了，模型会看到“读 A 的结果”挂在“读 B”下面。
  • 参数是模型生成的，不可信。必须用 JSON Schema 校验，并做路径/命令层面的安全检查。
  • 工具结果也是输入 token。返回 10 万行日志，下一轮就可能超窗；pi 的 read/bash 因此有截断。
  • 模型可以“假装”调用不存在的工具。运行时必须返回结构化错误，而不是崩溃。

流式场景更麻烦：工具调用的 JSON 是逐字符到达的，必须增量解析才能尽早显示“正在读取文件…”。pi 的 streaming-json.ts 就是为此写的部分 JSON 解析器；它在 toolcall_delta 阶段尽可能提取已完整的字段，在 toolcall_end 时做最终校验。

10.6推理模型：思考是输出的一部分

推理模型在给出最终答案前会生成一段“思考”。对不同 provider，这段内容可能是：

  • 可见的 thinking 块（Anthropic 的 extended thinking，可带签名）；
  • 摘要（只返回思考摘要，原文不暴露）；
  • 不可见但计费（reasoning tokens 计入 output）；
  • 加密/需回传（多轮工具调用时必须把加密推理块原样带回，否则模型丢失上下文）。

pi 用 thinkingLevelMap 把统一的档位（off/minimal/low/medium/high/xhigh/max）映射到各家的具体参数；null 表示该档位不支持。这样上层只需要说“这次用 high”，不必知道 Anthropic 是 budget_tokens、OpenAI 是 reasoning.effort。

成本直觉

思考 token 按 output 计费，而 output 单价通常是 input 的 3–8 倍。一个“想 30 秒”的请求，账单可能主要来自思考而不是回答。对简单任务强行拉高档位，是最常见的浪费。

10.7提示词缓存：把稳定前缀变成折扣

多数 provider 支持前缀缓存：如果本次请求的开头与上次逐 token 相同，这部分可以按缓存价读取（通常便宜 5–10 倍），写入则略贵。命中条件是严格的前缀匹配，因此顺序至关重要：

这解释了两个设计选择：

  1. 为什么 pi 把工具声明折进 system 消息：单一稳定前缀，顺序确定，便于缓存。
  2. 为什么系统提示要做“分段 diff”：只有变化的段落及其之后的内容失效，前面仍可命中。频繁改动开头的日期/时间会毁掉整个缓存。

Anthropic 还区分 5 分钟与 1 小时缓存：写入更贵，但适合长任务。pi 的 Usage.cacheWrite1h 与 Model.promptCache 就是为这个差异准备的；计费时 1h 写入按 2 倍输入价（见 10.2 的代码）。

10.8结构化输出：约束解码与“事后校验”

让模型稳定返回 JSON 有三条路：

方式机制可靠性
提示词要求“只返回 JSON”最弱；可能带 markdown 围栏或解释。
JSON mode服务端约束输出必须是合法 JSON中；不保证符合你的 schema。
Schema 约束解码按 JSON Schema/grammar 限制每个 token强；但支持度因 provider 而异，复杂 schema 可能降速。

pi 的工具参数采用“schema + 运行时校验”的组合：schema 发给 provider 争取约束解码，返回后仍用 TypeBox/Valibot 校验。原因是不同 provider 对 schema 的支持不完整（可选字段、union、嵌套 $ref 都可能被简化），不能把正确性完全托付给模型。

10.11成本与延迟：三个可观测指标

  • TTFT（time to first token）：用户感知的“卡不卡”。受输入长度、缓存命中、provider 负载影响。
  • 输出速度（tokens/s）：长回答的总时长主要由它决定。
  • 总 token：账单。输入通常占大头，尤其是多轮 agent。

优化顺序通常是：先减少无效工具结果（截断、grep 代替全文件读）→ 提高缓存命中（稳定前缀）→ 降低思考档位 → 最后才考虑换更小的模型。直接换小模型往往先损失工具调用正确率，反而增加重试成本。

10.12设计评价与检查点

pi 对模型层的抽象是“窄核心、宽适配”：核心只保留 agent 真正需要的概念（消息、工具调用、用量、停止原因），把 provider 的怪癖留在适配器。好处是上层稳定；代价是某些 provider 独有能力（例如特殊的缓存控制、原生结构化输出）需要额外的兼容字段才能透出。

对后端工程师来说，最重要的心态转变是：把模型当成一个昂贵、慢速、非确定、会犯格式错误的外部服务。所有分布式系统的老办法——超时、重试、幂等、校验、可观测性——在这里全部适用。
