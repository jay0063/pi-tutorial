Chapter 02 · pi-ai

把十几种模型
关进同一个协议

pi-ai 是整座建筑的地基。它不执行工具，也不管会话；它只回答一个问题：如何用一套类型与事件流，描述所有 LLM 的请求与响应？ 这一章拆开 Model、Message、AssistantMessageEventStream 和 provider 适配器。

阅读约 30 分钟 关键文件 5 个 代码：typebox / SSE

2.1为什么需要一层统一 API

不同厂商的接口在四个维度上互不兼容：

  • 消息形状：OpenAI 用 tool_calls 数组，Anthropic 用 tool_use content block，Google 用 functionCall part。
  • 流式协议：SSE 事件名、增量粒度、结束标记都不一样；有的厂商在流里给 usage，有的只在最后给。
  • 推理内容：thinking / reasoning summary / encrypted reasoning 的字段和回放规则不同。
  • 工具参数：有的返回完整 JSON，有的逐字符流式输出；有的支持 strict schema，有的只支持 grammar。

如果 agent loop 直接对接厂商 SDK，它会被这些差异污染，每加一个 provider 就要改循环。pi-ai 的策略是归一化到“消息 + 事件”：provider 适配器负责翻译，循环只认识统一协议。

设计取舍

归一化不是免费的。pi 的类型里保留了 textSignature、thoughtSignature、rawStopReason、compat 等厂商特有字段。这说明它选择的是“统一主干 + 保留逃生舱”，而不是追求纯净的抽象。对生产系统来说，这是更现实的做法。

2.2Model：一个数据对象，不是客户端

pi 里的 Model 是一个纯数据描述：id、provider、api、baseUrl、成本、上下文窗口、是否支持 reasoning、输入模态、provider 兼容参数。它不持有 HTTP 客户端，也不持有 API key。

packages/ai/src/types.ts ts
  • L854泛型参数是 API 名，不是厂商名。一个厂商可以有多个 API 形态（例如 OpenAI 的 completions 与 responses）。
  • L866thinkingLevelMap 把统一的 minimal…max 映射到各家的预算或 effort 档位，不支持就标 null。
  • L869contextWindow 与 maxTokens 是 harness 做压缩、限额、溢出恢复的依据。
  • L876compat 是条件类型：模型所属 API 决定兼容参数形状。这是 TypeScript 在“多态数据”上的典型用法。

模型目录由 *.models.ts 静态数据 + 运行时 catalog 组成。Models 是一个注册表：持有 provider、按 id 查模型、解析凭据、把请求分发给正确的 provider。

2.3Message：四种角色，一种可重放的历史

pi 的消息联合类型只有四种角色：system、user、assistant、toolResult。assistant 的内容是块数组：text、thinking、toolCall。toolResult 通过 toolCallId 与调用关联。

类型关键字段为什么这样设计
SystemMessagecontent、sections、toolsAdded / toolsRemoved系统提示与工具声明都放在 transcript 里，可增量 patch、可重放。
UserMessagetext / image 内容数组支持多模态与文件粘贴。
AssistantMessagecontent[]、usage、stopReason、api/provider/model记录“哪个模型、花了多少、为什么停”，可审计、可计费。
ToolResultMessagetoolCallId、content、isError、details模型看到 content；UI 与程序调用者看 details；结构化结果不污染上下文。

TranscriptContext：一个被品牌化的类型

对外 API 接受宽松的 Context（可以带 systemPrompt 与 tools 快捷字段）；但 provider 只接受 TranscriptContext。后者带一个不可伪造的 unique symbol 品牌，只有 normalizeContext() 能生产。

packages/ai/src/utils/transcript.ts ts
  • L31系统提示与工具定义被折进第一条 system 消息，而不是作为请求的旁路参数。这样它们也进入 transcript，能被持久化、重放、增量修改。
  • L33品牌类型让“未经归一化的 Context”在编译期就无法传给 provider，避免运行时才暴露协议错误。

这个设计带来一个不寻常但强大的能力：工具集可以随对话变化。后面的 SystemMessage.toolsAdded/toolsRemoved 记录增量；getCurrentTools() 顺序重放得到当前可用工具。对不支持“对话中途改工具”的 provider，适配器会折叠成一条前置 system 消息。

2.5EventStream：用 AsyncIterable 做背压友好的管道

provider 适配器是“生产者”，agent loop 是“消费者”。两者通过 EventStream 解耦：生产者 push，消费者 for await。它同时暴露一个 result() Promise，让只想拿最终消息的调用者不必消费整个流。

packages/ai/src/utils/event-stream.ts ts
  • L26两个 FIFO 队列：一个存事件，一个存等待中的消费者。push 时若有等待者就直接交付，否则入队；消费时若无事件就挂起。
  • L46isComplete 是注入的谓词。对 assistant 流，它检查 done / error；终止时顺手解析最终结果。
  • L72async * 生成器让调用方用 for await 消费，天然支持 break 与 AbortSignal 组合。
  • L86result() 让“只关心最终消息”的调用者可以忽略中间事件，而不会丢失终止信号。

它不是严格意义上的背压（生产端不会因为消费慢而暂停），而是一个无界缓冲 + 等待者队列。在 agent 场景里这是合理的：token 流很小，消费端通常就是当前进程；真需要背压时，用 AbortSignal 取消更简单。

2.6Provider 适配器：统一契约，差异下沉

Provider 接口把“模型目录 + 认证 + 流 + 可选能力”打包在一起。Models 负责解析 auth、合并 headers、归一化 context，然后调用 provider.streamSimple()。适配器内部通常做四件事：

  1. 把统一的 Message[] 转成厂商 payload（工具 schema、图片、system、cache 标记）。
  2. 发起请求，处理认证、超时、重试、代理。适配器通常把 SDK 自带重试关掉（maxRetries: 0），交给统一策略。
  3. 消费 SSE / WebSocket，把厂商事件翻译成 AssistantMessageEvent。
  4. 在终止时计算 usage、cost、stopReason，发出 done 或 error。

  • L581-582适配器先解析 transcript 的“有效形态”：是否需要把 system 消息折叠到开头，以及当前工具集。工具声明从 system 消息里重放得到。
  • L586output 是唯一可变的消息对象；所有 partial 都指向它。消费端必须把它当只读快照使用。

流式工具参数：为什么不能直接 JSON.parse

模型返回的 tool call 参数是逐段到达的。中途文本通常是非法 JSON：{"path":"src/se。适配器不能等流结束才更新 UI，因为工具调用的参数预览、权限确认都需要尽早展示。

pi 的 StreamingJsonParser 是一个容错的增量解析器：未闭合的字符串显示已读字符，未闭合的对象显示已有成员，非法转义保留为字面量，永远不抛异常。它还通过“复制信用”限制大对象快照的开销：snapshot() 可能返回旧快照，保证总工作量与输入长度线性相关。

packages/ai/src/utils/streaming-json.ts ts
  • L127单次扫描：每段文本只读一遍，字符串、标量、结构字符三种状态机。复杂度 O(输入长度)。
  • L146信用机制：不是每次 append 都重新拷贝整个开放容器；信用不够时返回上一个快照。大数组场景下 UI 预览会略微滞后，但总成本有上界。
  • L153最终仍用 parseToolCallArguments() 完整解析一次；增量解析只用于预览，不能替代严格校验。

最终，AgentToolCall.arguments 可能带着 argumentsError。agent loop 的参数校验会把这个错误变成模型可见的 toolResult，让它重试——这是“错误也是上下文”的一个具体例子。

2.7重试、成本与那些“不统一”的细节

pi-ai 把 provider 错误分为可重试与不可重试两类，用一组正则匹配错误文本：429/5xx、overloaded、rate limit、连接中断、流提前结束等可重试；配额耗尽、账单问题、订阅限制不可重试。适配器默认关闭 SDK 自带重试（maxRetries: 0），避免两层重试叠加。

  • 延迟上限：maxRetryDelayMs 默认 60s；服务端要求的等待超过上限就立即失败，交给上层带用户提示的重试。
  • 流中失败：已经 start 后出错，仍然通过 error 事件返回一个 stopReason: "error" 的 assistant 消息，而不是 reject Promise。
  • 成本：calculateCost() 支持阶梯定价、1h 缓存写入按 2× input 计费；usage 里保留 cacheRead/cacheWrite，方便分析 prompt cache 命中率。
  • 思考档位：统一为 off/minimal/low/medium/high/xhigh/max，由 thinkingLevelMap 映射；不支持的档位会被 clamp 到最近的可用档。

2.8这一层的代价与边界

pi-ai 的设计很务实，但不是“零成本抽象”：

  • 类型很大：types.ts 接近千行，包含大量可选字段。读的时候要区分“核心协议”和“厂商逃生舱”。
  • 事件顺序需要信任适配器：协议规定了顺序，但运行时没有强校验；一个写错的扩展 provider 可能发出非法序列。
  • “simple” 与 “full” 双入口：stream 保留厂商选项，streamSimple 提供统一档位。简单场景用后者，复杂场景用前者。
  • 工具声明在 system 消息里：这是 pi 的特色，也让“中途换工具”成为可能；但要求 provider 支持 mid-conversation system，否则适配器要折叠。
