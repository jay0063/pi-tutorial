TUI 差分渲染
Chapter 08 · pi-tui

终端不是画布，
是一条会滚动的日志

在终端里做流式 UI，难点不是“画出来”，而是只改该改的行：不闪屏、不破坏滚动历史、不把光标弄丢。pi-tui 自己实现了组件模型、布局树和行级 diff，只依赖 ANSI 转义序列。

8.1为什么不直接用 Ink / React

把一个 React 渲染器塞进终端，会得到“每次状态变化重绘整棵树”的模型。对聊天流式输出，这有三个问题：

  • 闪屏：整屏重写会让终端不断滚动/闪烁，尤其是在慢速 SSH 上。
  • 滚动历史被破坏：用户向上翻看时，重绘会把视口拉回底部。
  • 成本高：每个 token 都触发一次虚拟 DOM diff，CPU 浪费在不变的行上。

pi 的选择是“组件返回字符串数组，渲染器做行级 diff”。没有虚拟 DOM，没有 reconciliation；组件自己决定在给定宽度下输出哪些行。

8.2组件契约：一个函数，宽度进、行数组出

  • L124返回的是“屏幕行”，不是逻辑段落。自动换行、截断、边框都由组件自己处理。
  • L127输入处理是可选的；焦点由容器管理。组件不需要知道事件循环。
  • L141invalidate() 清缓存。主题切换、字体宽度变化时必须调用，否则会复用旧颜色/旧宽度。

组件之上是布局节点。pi 不要求组件继承某个基类，而是用 Symbol.for("@earendil-works/pi-tui/layout-node") 做能力探测：实现了这个方法的组件参与布局，否则按固定行数处理。这避免了深继承，也允许第三方组件只实现 render。

布局节点行为用途
vstack垂直堆叠；每项有 basis/grow/shrink/min/max主对话流 + 输入框 + 状态栏。
hstack水平排列；支持对齐与间距侧栏、状态行、并排 diff。
scroll视口裁剪、滚动状态、内容宽度长对话、帮助面板、日志。

布局计算带按组件与宽度缓存：同一组件在同一宽度下只渲染一次。这对流式场景很关键——每帧只有少数组件的内容变了，其余直接复用行数组。

8.3主屏 vs 备用屏

pi 有两种 TUI 实现：

  • 主屏（TuiMainScreen）：内容写入终端正常缓冲区，保留 scrollback。用户可以用终端自身的滚动条/快捷键翻历史。适合“对话式”长输出。
  • 备用屏（TuiAltScreen）：切换到全屏备用缓冲区，退出时恢复。适合全屏编辑器/仪表盘。

主屏的难点在于视口会随内容增长而滚动。渲染器必须知道“上一次视口顶部”和“硬件光标所在行”，否则 diff 的坐标会错位。这就是 previousViewportTop、hardwareCursorRow 这些字段存在的原因。

8.4行级 diff：找到变化区间

doRender() 的第一步是把整棵组件树渲染成新行数组；然后与上一帧逐行比较，找到第一个和最后一个变化的行。中间没变的部分不重写。

packages/tui/src/tui-main-screen.ts ts
  • L364-365只记录区间边界，不保存每行 diff。对终端来说，重写区间内的少量未变行通常比精确 patch 更便宜。
  • L367取两边长度的最大值；新增行与旧的空串比较，删除行与新的空串比较。
  • L376-380如果只是追加（常见于流式输出），把区间强制扩到末尾。这允许“追加优化”：不用重写旧行，直接在末尾输出。
  • L385Kitty 图像占多行且用占位符表示，必须把整个图像块纳入变化区间，否则会留下残影。

什么时候放弃 diff，整屏重绘

以下情况会触发 fullRender(true)：

  • 宽度或高度变化（resize）；
  • 第一个变化行在上一次视口顶部之上——那里已经滚出屏幕，无法原地修改；
  • 删除的行数超过一屏；
  • 内容缩短且启用了 clearOnShrink，且没有浮层；
  • 浮层/模态框改变了合成结果。

整屏重绘被包裹在 \x1b[?2026h … \x1b[?2026l（synchronized output）之间。支持这个私有模式的终端会把整帧原子呈现，避免撕裂。不支持的终端会忽略序列，退化为普通写。

为什么是“从第一个变化行重写到末尾”

终端不能随机访问任意行：要改第 3 行，必须先移动光标；要改第 3 行之后的内容，重写尾部通常比逐行跳跃更可靠，也能自然处理行数变化。区间 diff 的真正收益是保留上方的 scrollback 与视口位置，而不是节省几个字节。

8.516ms 节流与输入优先

模型每个 token 都会触发一次状态更新。如果每次都渲染，CPU 会被吃满。pi 把普通渲染限制在最多约 60fps：

packages/tui/src/tui.ts ts
  • L1027requestRender() 是幂等的：一帧内多次请求只安排一次。注意它不立即渲染，而是先 nextTick，让同一轮事件循环里的多次更新合并。
  • L1029force 会清空渲染状态并走立即渲染，用于 resize、主题切换等不能等一帧的场景。
  • L1043输入优先：键盘输入不能等 16ms 的节流计时器（Windows 上 setTimeout(0) 可能就是一整帧），所以另走一条立即渲染路径，并取消已排队的节流帧。
  • L1046注释记录了一个真实竞态：先排队的 scheduleRender 可能已经创建 timer，必须显式取消。

scheduleRender() 用 lastRenderAt 计算剩余时间：delay = max(0, 16 - elapsed)。渲染后如果又有请求，会再排一帧，保证最终状态不会丢。

8.6光标、浮层与图片

  • 假光标：组件可以在行内放一个标记，渲染器在合成后解析成真实光标位置；这样嵌套组件不需要知道终端坐标。
  • 硬件光标：showHardwareCursor 控制是否显示。输入框需要真实光标，流式输出时通常隐藏以减少闪烁。
  • 浮层：模态框/补全菜单在行数组合成阶段叠加，而不是插入组件树。这样它们不会影响底层布局，关闭时也不需要重排。
  • Kitty 图像：图片以占位符行表示，渲染器记录图像 id 与占用行数；变化时删除旧图、重绘新图。删除区间必须覆盖整个图像块。
  • 宽字符：visibleWidth() 按 grapheme cluster 计算终端列宽，而不是 string.length；中日韩字符、emoji、组合符号都按实际宽度处理。

8.8设计评价

pi-tui 是一个“足够小、足够可控”的终端 UI 层。它没有追求通用 GUI 框架的能力，而是围绕三个约束设计：

  1. 终端是流：只追加、少重写、保护 scrollback。
  2. 输入必须跟手：渲染可以节流，键盘不能。
  3. 组件是无状态渲染函数：给定宽度就能算出完整行数组，便于缓存与测试。

代价是：复杂布局（例如自适应表格、嵌套滚动）需要手工计算；组件作者必须理解 ANSI、宽字符与裁剪。它不适合做富交互界面，但对 coding agent 这种“长日志 + 一个输入框 + 偶尔浮层”的形态，恰好合适。
