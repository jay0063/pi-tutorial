类型不是注释，
是运行时的合同

pi 把大量正确性放进类型系统：消息联合、事件状态机、provider 差异、扩展自定义消息。这一章不教语法，而是用 pi 的真实代码解释为什么这样写，以及你能从中带走哪些模式。

9.1先读 tsconfig：一份设计声明

pi 的 tsconfig.base.json 只有二十来行，却透露了很多取向：

{
  "compilerOptions": {
    "target": "ES2024",
    "module": "Node16",
    "lib": ["ES2024"],
    "strict": true,
    "erasableSyntaxOnly": true,
    "verbatimModuleSyntax": true,
    "allowImportingTsExtensions": true,
    "rewriteRelativeImportExtensions": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  }
}
选项含义影响
strict全套严格检查禁止隐式 any、严格空值、严格函数类型。pi 的代码几乎没有 any 滥用，靠的就是这个。
erasableSyntaxOnly只允许“擦除后不留下运行时代码”的语法不能用 enum、namespace、构造函数参数属性。这让 Node 的原生类型剥离可以直接跑源码。
verbatimModuleSyntax导入/导出原样保留类型导入必须写 import type，否则运行时可能保留不存在的导出。
allowImportingTsExtensions允许 import "./x.ts"源码里直接引用 .ts，开发者不需要记住构建后的文件名。
rewriteRelativeImportExtensions构建时把 .ts 改成 .js发布产物仍是标准 ESM，Node 能直接运行。

这套组合的目标很明确：源码即运行时代码。没有装饰器元数据、没有 enum 对象、没有路径别名魔法，Node 22 的类型剥离可以直接执行 .ts。代价是失去一些“编译期便利”，换来更简单的调试与更快的启动。

9.2可辨识联合：事件状态机的骨架

AssistantMessageEvent 是 pi 里最典型的可辨识联合。每个成员都有一个字面量 type，其余字段随类型变化：

packages/ai/src/types.ts ts
  • L822-831流式事件都带 partial：到目前为止的完整消息。消费者不需要自己拼状态。
  • L832Extract<StopReason, ...> 把 done 的 reason 限制为“正常结束”的子集；error 则限制为错误/中止。这比在运行时检查更早暴露错误。
  • L837error 事件没有 partial，而是完整的 error 消息——终止状态携带最终结果，而不是中间快照。

消费端因此可以写穷尽 switch。TypeScript 会根据 type 自动收窄字段；如果你漏了一个分支，把剩余值赋给 never 就会编译失败：

packages/coding-agent/src/core/messages.ts ts
  • L189-192这是“穷尽性检查”的惯用法：如果未来新增一种消息角色而这里没处理，m 的类型就不是 never，赋值失败。
  • L184-187基础 LLM 消息直接透传；自定义消息在此前已被转换成 user/toolResult 等形态。

9.3条件类型：让数据形状跟着 API 变

不同 provider 的兼容参数完全不同。pi 没有用一个巨大的可选字段包打天下，而是让 Model 的 compat 字段由泛型参数决定：

packages/ai/src/types.ts ts
  • L876条件类型按 API 名分发。当 TApi = "anthropic-messages" 时，compat 的类型就是 AnthropicMessagesCompat，IDE 能给出精确补全。
  • L886未知 API 落到 never，意味着不能传 compat。要支持新 API，必须显式加分支——这是有意的“封闭扩展”。
  • Model<TApi>整个接口都带这个参数，因此模型目录、适配器、工具都能共享同一份精确类型。

同类技巧也用在 stream options 上：ApiStreamOptions<TApi> 先查 ApiOptionsMap，命中就用该 API 的选项类型，否则退回通用 StreamOptions & Record<string, unknown>。这让简单调用保持类型安全，又允许自定义 provider 传额外字段。

9.4品牌类型：让“未归一化”无法通过编译

pi 的 provider 只接受 TranscriptContext，而不是任意 Context。区别是一个编译期品牌：

packages/ai/src/types.ts ts
  • L792unique symbol 无法在别处重新声明，因此外部代码无法伪造这个属性。它不是运行时字段，只存在于类型层。
  • L800-803归一化后的类型只暴露 messages；systemPrompt 与 tools 已经被折进 system 消息。
  • L33（transcript.ts）唯一的生产者是 normalizeContext()：return { messages } as TranscriptContext。这个 as 是受控的“类型逃生舱”，集中在一处。

品牌类型的价值在于把运行时约定前移到编译期。没有它，一个忘了归一化的调用要等到 provider 收到缺系统提示的请求才暴露；有了它，编辑器立刻报错。

9.5泛型与 TypeBox：一份 schema，两种用途

工具参数用 TypeBox 定义。它既是运行时的 JSON Schema（发给 provider 做约束采样/校验），也是编译期的类型来源：

const readSchema = Type.Object({
  path:   Type.String({ description: "Path to the file to read (relative or absolute)" }),
  offset: Type.Optional(Type.Number({ description: "Line number to start reading from (1-indexed)" })),
  limit:  Type.Optional(Type.Number({ description: "Maximum number of lines to read" })),
});

export type ReadToolInput = Static<typeof readSchema>;
// { path: string; offset?: number; limit?: number }

这里有三层泛型协作：

  1. Type.Object() 返回一个携带静态类型的 schema 对象；
  2. Static<T> 把 schema 类型映射成普通对象类型；
  3. AgentTool<TParameters> 用 Static<TParameters> 约束 execute 的 params。

结果：你只写一次字段定义，运行时校验和编译期补全自动一致。改字段名时，忘改 execute 里的解构会立刻报错。

defineTool() 是另一项技巧：它保留字面量推断。直接写对象字面量传给 registerTool，params 可能被上下文类型放宽为 unknown；defineTool 通过泛型约束把具体 schema 的类型保留下来。

9.6AsyncIterable：把流变成可组合的序列

EventStream 实现了 AsyncIterable<T>，因此消费者可以写：

for await (const event of stream) {
  if (event.type === "text_delta") process.stdout.write(event.delta);
  if (event.type === "done") break;
}
const final = await stream.result();

这比回调好在三点：

  • 背压的语法位置：await 天然让消费慢下来（虽然 EventStream 内部是无界缓冲，但接口允许未来换成有界实现）。
  • 取消：break 会调用迭代器的 return()，生产者可以据此清理。
  • 组合：可以写 for await 嵌套、Promise.race、超时包装，而不需要适配回调协议。

注意实现里的一个细节：async *[Symbol.asyncIterator]() 生成器与 result() Promise 并存。这允许“只关心最终消息”的调用者不消费流，同时不阻塞生产者。

9.7声明合并：让扩展增加消息类型

pi 的 AgentMessage 默认只有四种 LLM 消息，但扩展可以注入自定义消息（例如 todo、artifact）。实现方式是“空接口 + 索引访问”：

packages/agent/src/types.ts ts
  • L365-367空接口不是“没用的占位”，而是给模块增强留的插槽。接口声明合并会把扩展字段加进来。
  • L374keyof CustomAgentMessages 取出所有键，再用索引访问得到所有自定义消息的联合。空接口时 keyof 是 never，所以联合就是基础 Message。
  • L358示例里的模块名是旧包名；实际使用时写当前包名。声明合并是全局的，整个进程内所有扩展共享同一套消息类型。

这也解释了为什么 convertToLlm() 里的 switch 需要 _exhaustiveCheck: never：一旦扩展增加了新角色，编译器会强制你处理它，否则自定义消息会悄悄变成 undefined。

9.8satisfies：检查而不拓宽

普通类型注解会把字面量拓宽成基础类型；satisfies 只做兼容性检查，保留字面量推断：

const finalized = {
  toolCall,
  result: createErrorToolResult("Operation aborted"),
  isError: true,
} satisfies FinalizedToolCallOutcome;

这样 finalized.result 的精确类型（而不是 any）被保留，后续访问字段有补全；同时编译器仍会检查对象是否符合 FinalizedToolCallOutcome。pi 在 loop、工具结果、provider 适配器里大量使用这个模式。

另一个常见组合是 as const：

export const readToolSystemPromptContribution = {
  snippet: "Read file contents",
  guidelines: ["Use read to examine files instead of cat or sed."],
} as const;

as const 让字符串字面量与数组变成只读精确类型，避免被推断成 string 或 string[]，从而能安全地拼进系统提示而不被意外修改。

9.9NodeNext / ESM：包边界就是 API 边界

每个 package 都是 "type": "module"，并通过 exports 映射暴露入口：

{
  "name": "@earendil-works/pi-agent-core",
  "type": "module",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" }
  }
}

这带来几个约束：

  • 相对导入必须带扩展名（源码写 .ts，构建后重写为 .js）。
  • 不能在 ESM 里用 __dirname；pi 用 import.meta.url。
  • 类型导入用 import type，否则 verbatimModuleSyntax 会保留运行时导入。
  • 包的公共 API 由 exports 决定；深层路径不暴露，防止外部依赖内部结构。

这套边界对 agent 项目很重要：provider 适配器、TUI、工具都通过明确的包接口协作，而不是互相 ../../ 乱穿。读源码时，先看 exports 与 index.ts，能快速判断哪些是稳定 API、哪些是内部实现。

9.10可以带走什么

用联合表达状态

不要用一堆布尔字段表示“正在流式/已完成/出错”。一个带 type 的联合让非法状态无法构造。

把不变量放进类型

品牌类型、never 分支、Extract 子集，都是把运行时约定前移的手段。

一份 schema 两处用

TypeBox/JSON Schema + Static 避免“校验一套、类型一套”的漂移。

让扩展点类型安全

空接口 + 声明合并 + 穷尽检查，可以在不修改核心的情况下增加消息类型。
