一个循环，
三种“继续”的理由

agent loop 的全部难点不在“调用模型”，而在什么时候再调用一次。pi 用双层 while、两个队列和三个钩子，把“有工具结果”“用户插话”“用户追加任务”这三种继续理由分得清清楚楚。

3.1先把三个词钉死

读循环之前，必须区分三个时间尺度。pi 的类型注释里写得很明确：

事件顺序对应如下。注意 message_start/end 对每条消息都发，而 message_update 只在 assistant 流式期间发，且携带原始的 AssistantMessageEvent：

agent_start
└─ turn_start
   ├─ message_start   (user / steering / follow-up)
   ├─ message_end
   ├─ message_start   (assistant)
   ├─ message_update  ← text_delta / toolcall_delta / ...
   ├─ message_end
   ├─ tool_execution_start
   ├─ tool_execution_update   (可选，多次)
   ├─ tool_execution_end
   ├─ message_start   (toolResult)
   └─ message_end
└─ turn_end
agent_end
为什么 agent_end 也带 messages

agent_end 携带整个 run 新增的消息数组。这样订阅者可以在一个事件里完成落盘，而不必自己维护增量。这个数组也是 EventStream<AgentEvent, AgentMessage[]> 的最终结果。

3.2双层循环：内层处理工作，外层处理“再来一轮”

runLoop() 是 agentLoop() 与 agentLoopContinue() 的共同实现。它只有两个循环，但职责划分非常精确。

packages/agent/src/agent-loop.ts ts
  • L188外层只为 follow-up 存在。内层退出意味着“没有工具、没有 steering”，此时才检查 follow-up 队列；有就塞回 pendingMessages 并 continue。
  • L192内层条件是两个布尔量：还有工具调用，或还有待注入消息。初始 hasMoreToolCalls = true，所以第一次一定进入。
  • L195prepareNextTurn 是产品层插入的钩子（压缩、模型切换、上下文重建都在这里）。它可以替换 context 并附加系统消息。
  • L210-215一句注释揭示了一个真实 bug 的修复：准备过程可能很久（压缩），期间用户可能插话。只在先前没有拿到 steering 时才再轮询，否则 one-at-a-time 模式会一次交付两条。

一次迭代的主体是“准备 → 请求 → 流式响应 → 工具 → 终结”。终结部分决定了循环是否继续：

packages/agent/src/agent-loop.ts ts
  • L295finishTurn 在 turn_end 之前运行，但它的决策在 turn_end 之后才生效。这样订阅者看到的 turn_end 仍是完整的一轮。
  • L298end 是硬退出：不轮询 steering，也不轮询 follow-up。适合“预算耗尽”“检测到终止条件”等场景。
  • L303-307continue 只是“希望再请求一次”；如果工具或 steering 已经保证了这一点，就把显式意图清掉，避免多跑一轮空请求。
  • L311follow-up 只在 agent 本来就要停时检查。它不是插话，语义是“你干完之后再做这个”。

硬退出：错误与中断

如果 assistant 消息的 stopReason 是 error 或 aborted，循环会走另一条路径：调用一次 finishTurn（其决策被忽略）、发 turn_end 与 agent_end、立即返回。这是刻意的：错误不能被 follow-up 队列悄悄“续命”，否则会无限重试。

3.3工具调用流水线

一次工具调用要穿过六个阶段。把“查找工具、解析参数、校验 schema、权限钩子”都放在执行之前，意味着被拒绝的调用也会得到一条结构化的 toolResult，模型能看见原因并修正。

packages/agent/src/agent-loop.ts ts
  • L726查找失败不是抛异常，而是返回一个“立即结果”。这让上层代码只有一条路径：处理结果。
  • L736prepareArguments 给工具一个机会修正/规范化原始参数（例如补默认值、解开别名），然后才做 schema 校验。
  • L738beforeToolCall 是权限、沙箱、审计的插入点。它拿到的是已校验的参数，不需要自己再防御。
  • L756block 的结果可以带 terminate；是否提前结束由整批结果共同决定。
  • L780整个 try/catch 覆盖参数准备与钩子：钩子抛错也会变成模型可见的错误结果，而不是让 run 崩溃。

执行：更新、计时与取消

executePreparedToolCall() 给工具传三个东西：调用 id、校验后的参数、AbortSignal，以及一个 onUpdate 回调。工具可以多次报告部分结果（例如 bash 的增量输出），循环会把它们转成 tool_execution_update。

packages/agent/src/agent-loop.ts ts
  • L846performance.now() 是单调时钟，不受系统时间调整影响；durationMs 会进入事件与 toolResult。
  • L853更新回调先收集为 Promise，执行结束后统一 await。这保证 tool_execution_end 不会抢在最后一条 update 之前。
  • L860acceptingUpdates = false 是一道闸门：工具在返回后仍异步调用 onUpdate 也不会污染事件流。
  • L855-863工具抛错被规范化为错误结果。注意：AbortSignal 触发时工具通常抛 AbortError，同样落到这里。

结果消息：content 给模型，details 给程序

createToolResultMessage() 把执行结果转成 transcript 里的消息。这里有一个小而关键的分工：

  • content：模型看得见的文本/图片，进入下一次请求的上下文。
  • details：结构化的完整结果，供 UI 渲染、扩展读取、日志分析，不进入模型上下文。
  • usage：工具自身消耗的 token/费用（例如子 agent），计入整轮成本。

这样设计避免了“为了 UI 好看而把大 JSON 塞进上下文”的常见浪费。工具作者可以返回丰富的 details，同时只给模型一句摘要。

3.4并行执行，但顺序落盘

默认的 toolExecution 是 parallel。但“并行”有三个精确的限定：

  1. 预检串行：每个调用依次执行 prepareToolCall。这样权限钩子看到的顺序是确定的，UI 也能按源顺序显示。
  2. 只要有一个工具声明 executionMode: "sequential"，整批串行。这是“批次级”约束，不是“该工具单独串行”。
  3. 结果按 assistant 源顺序生成消息，尽管完成事件按实际完成顺序发出。
packages/agent/src/agent-loop.ts ts
  • L525只挑出 type: "toolCall" 的块；同一个 assistant 消息里的文本与思考块不参与执行。
  • L526-528“存在任一 sequential 工具”就整批降级。这避免了同一文件被并行读写导致的竞态，代价是牺牲了其他工具的并行度。
  • L529决策是纯函数式的：只看配置与工具声明，不看运行时状态。容易测试，也容易预测。

并行分支的实现有一个值得注意的技巧：它先同步地做预检，把每个已准备调用包成一个 thunk（() => Promise<Outcome>），立即完成的调用则直接放入结果。最后用 Promise.all 一次性启动所有 thunk。

packages/agent/src/agent-loop.ts ts
  • L631thunk 里再查一次 signal.aborted：预检可能耗时，期间用户可能取消。已取消的调用仍产生一条错误结果，保持“每个 toolCall 都有回应”。
  • L655Promise.all 保持数组顺序，即使完成顺序不同。这是“并发执行、顺序收集”的标准写法。
  • L661只有收集完成后才逐条发 toolResult 消息事件。因此 turn_end.toolResults 与 assistant 源顺序一致，模型看到的上下文也稳定。
  • L640tool_execution_end 在各自完成时立即发出，不受顺序约束。UI 可以实时显示“哪个先跑完”。

并行总耗时 ≈ 最慢的那个；串行是三者之和。实际延迟还受预检与网络影响。

terminate：整批一致才提前结束

工具结果可以带 terminate: true，表示“不需要再让模型继续”。但循环用的是 every()，不是 some()：

function shouldTerminateToolBatch(finalizedCalls) {
  return finalizedCalls.length > 0 &&
    finalizedCalls.every(f => f.result.terminate === true);
}

这意味着一个工具不能替其他工具做决定。只有整批都认为“结束”，才跳过后续自动请求。混合批次继续，防止某个保守的工具意外截断整轮工作。

3.5Steering 与 Follow-up：两种“插话”

这是 pi 最容易被误解的部分。两个队列都装用户消息，但语义完全不同：

SteeringFollow-up
时机agent 运行期间随时可入队；在当前工具批处理全部结束后注入agent 本来要停止时才检查
语义“方向不对，改做这个”“做完之后，再做这个”
是否打断当前 assistant 消息不会。已发出的工具调用全部执行完不会。它等当前工作自然结束
循环位置内层：每轮结束后轮询，作为下一轮的输入外层：内层退出后轮询，塞回内层
模式steeringMode：one-at-a-time / allfollowUpMode：one-at-a-time / all
“打断”其实是“不开始下一轮”

用户按下 Esc 或发送 steering，不会杀死正在执行的 bash。真正的取消要传 AbortSignal。pi 的设计假设是：工具执行应当原子完成，否则文件可能处于半写入状态。需要强取消时，工具自己监听 signal。

3.7设计评价：克制带来的可组合性

pi-agent-core 的循环只有约 160 行，但它把几个容易纠缠的决策分开了：

  • 循环不知道压缩、模型切换、会话持久化。这些通过 prepareNextTurn / prepareRequest / finishTurn 注入。
  • 工具失败不是控制流异常。所有失败都变成 isError 结果，循环只有一条路径。
  • “继续”被拆成三个来源：工具结果、steering、follow-up。每个来源的检查位置不同，避免优先级混乱。
  • 顺序保证显式化：预检顺序、完成事件顺序、结果消息顺序，三者各有明确规则。

代价是：prepareNextTurn 与 finishTurn 的时序很微妙（尤其与压缩、队列、错误交互），扩展作者必须理解这些钩子；否则容易出现“压缩后消息重复”“错误后又被 follow-up 拉起”之类的问题。这也是为什么产品层的 AgentSession 需要单独一章。
