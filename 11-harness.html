模型之外的一切，
才是你的产品

同一个模型，放进不同的 harness，表现可以差一个数量级。工具怎么描述、上下文怎么裁剪、失败怎么恢复、人怎么介入——这些工程决策决定了 agent 是否真的可用。这一章讨论设计空间，以及 pi 为什么选了现在这条路。

阅读约 30 分钟 设计取舍 含安全边界

11.1Harness 到底是什么

把 LLM 本身看作 CPU：它只会根据输入预测输出。Harness 是围绕它的一整套运行时：

  • 循环：什么时候再请求一次，什么时候停。
  • 工具：提供哪些能力、如何描述、如何执行、结果如何裁剪。
  • 上下文：系统提示、历史、压缩、检索、分支。
  • 接口：终端、JSON、RPC、SDK；人如何看到进度、如何打断。
  • 持久化：会话如何保存、恢复、分叉、审计。
  • 扩展：第三方如何加工具、改行为、接外部系统。
  • 安全：谁能执行什么，边界在哪里。

一个残酷的事实：模型能力越强，harness 的瓶颈越明显。模型已经会写代码，但如果工具返回一万行日志、压缩把关键约束丢了、中断后无法恢复，它依然做不完任务。

11.2职责分层：pi 的答案

这个分层最重要的性质是可替换：

  • 换 provider，不动 loop；
  • 换 UI，不动 session；
  • 加工具，不动核心；
  • 换存储，不动循环（只要实现同样的会话接口）。

pi 没有把所有东西塞进一个大 Agent 类，而是让 AgentSession 组合 Agent、SessionManager、Settings、ExtensionRunner。组合比继承更容易替换，也更容易测试。

11.3把契约写进类型：AgentLoopConfig

loop 不直接依赖 session，而是依赖一组回调。这个接口就是 harness 的“插座”：

packages/agent/src/types.ts ts
  • L194loop 需要一个模型，但不关心它是哪家。provider 差异在 pi-ai 内部消化。
  • L203“不得抛异常”被写进契约。转换函数一旦抛错，loop 会产生不完整的事件序列，UI 与持久化都会错位。失败要返回安全回退值。
  • L236-244transformContext 是上下文管理的入口：裁剪、注入、检索都在这里，且发生在转换之前。
  • L258-264finishTurn 把“是否继续”的决策交给上层。loop 提供机制，session 决定策略（例如重试、压缩后继续、或直接结束）。

注意这些回调的失败语义：除了 finishTurn 这类显式控制点，大多数钩子被设计成“可失败但不致命”。扩展的 tool_call 处理器是例外——它决定工具是否执行，出错时选择 fail closed（见第 07 章）。

11.4设计空间：pi 的取舍

维度pi 的选择替代方案代价 / 收益
产品形态最小核心 + 扩展大而全的固定工作流上手简单、可定制；但需要用户自己拼能力。
子 agent不内置内置 planner/executor/reviewer核心简单、上下文可控；复杂任务要自己扩展。
计划模式不内置独立的 plan/act 两阶段避免“计划漂移”；但少了强制审查点。
权限无内置沙箱细粒度 allow/deny + 审批信任用户环境；安全需靠容器化。
会话append-only 树可变数据库行分支/审计/恢复强；存储会增长。
扩展加载同进程 jiti独立进程 + RPC零序列化开销；扩展拥有完整权限。
UI自研差分 TUIWeb / Electron轻、SSH 友好；复杂交互受限。
工具执行默认并行，可标顺序全部串行快；但需要处理竞态与顺序依赖。

这些选择不是“对/错”，而是把复杂度放在哪里。pi 把复杂度推到扩展作者和容器边界，换取核心的可读性与可替换性。对个人开发者，这是友好的；对需要强合规的团队，则需要在外围补齐审批与隔离。

11.5上下文管理：harness 的核心竞争力

同一个模型，上下文组织得好不好，任务完成率差别巨大。pi 的做法可以概括为四层：

  1. 系统提示分段：基础行为、工具说明、项目上下文、技能、动态提醒，各自独立成段，便于 diff 与缓存。
  2. 工具结果截断：read 默认最多 2000 行 / 50KB；bash 输出同样有上限，并提示模型“结果被截断”。
  3. 压缩：接近窗口上限时，把旧历史替换成摘要 + 最近保留区，原始记录仍在 JSONL 中。
  4. 分支与投影：会话是树，当前上下文只是从根到叶的一条路径；切换分支不需要重写历史。

第 05 章详细讲了投影算法。这里强调一个设计原则：压缩不是删除。原始消息永远保留，摘要只是“当前视图”的一部分。这让用户可以在压缩后回溯、分叉、甚至手动编辑上下文。

11.6失败处理：agent 的日常

在 agent 里，失败是常态而非异常。一个成熟 harness 至少要处理：

失败表现pi 的处理
网络/限流请求报错、429pi-ai 按 provider 策略重试；可重试错误带退避。
流中断已收到部分文本产生 error 消息；上层决定重试还是保留部分结果。
工具报错命令非零退出、文件不存在转成 isError: true 的 toolResult，让模型自己修正。
参数不合法JSON 不符合 schema校验失败，返回结构化错误，不执行副作用。
输出截断stopReason === "length"该批次所有工具调用判为失败，避免执行半截参数。
上下文溢出provider 报超窗触发压缩/裁剪，必要时丢弃最旧轮次。
用户中止Ctrl-C / abortAbortSignal 贯穿请求与工具；产生 aborted 消息。

一个容易忽略的点：工具错误要返回给模型，而不是抛给用户。模型看到“文件不存在”，会自己换路径；用户看到红色堆栈，只会困惑。pi 的 createErrorToolResult() 就是把这类失败转成模型可读的文本。

11.7安全边界：信任模型，还是信任沙箱

这是 harness 设计里最容易被低估的部分。pi 的 README 写得很直接：

Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access. By default, it runs with the permissions of the user and process that launched it.

If you need stronger boundaries, containerize or sandbox Pi.

换句话说：安全边界不在 agent 内部，而在进程/容器边界。这有两种完全不同的哲学：

  • 审批式：每个危险操作弹窗，用户点“允许”。优点是细粒度；缺点是打断心流，且用户会习惯性点允许。
  • 隔离式：agent 在容器/虚拟机里随便跑，边界由内核保证。优点是无需打断；缺点是需要基础设施。

pi 选择后者，并提供三种容器化模式（见 docs/containerization.md）：

  1. Gondolin 扩展：pi 与 provider 凭证留在宿主机，内置工具和 ! 命令路由进本地 Linux micro-VM。
  2. 纯 Docker：整个 pi 进程跑在容器里，简单直接。
  3. OpenShell：在策略控制的沙箱中运行，适合企业环境。
扩展 = 任意代码执行

pi 的扩展在同一进程内加载，拥有与 pi 相同的权限。安装第三方扩展等同于运行一个 npm 包。第 07 章讲过 jiti 的加载机制；它能加载 TypeScript，但不是沙箱。不要把“扩展”误认为“受限插件”。

11.8可扩展性的阶梯

pi 把定制分成几个层级，复杂度递增：

层级能做什么不改代码适合
Prompt template预置一段提示词/参数是重复性任务、团队规范。
Skill按需加载的说明与脚本是领域知识、操作手册。
Extension加工具、命令、钩子、UI是接内部系统、改工具行为。
Package把以上打包分发是团队共享、npm 发布。
Fork / SDK改核心、嵌入自有产品否深度定制、产品集成。

这个阶梯的好处是升级路径清晰：先写提示词，不够再写 skill，再不够写扩展，最后才 fork。大多数人停在前两层，核心因此能保持稳定。

11.9“不做什么”也是设计

pi 明确不内置 sub-agents 和 plan mode。这不是能力缺失，而是对复杂度的控制：

  • Sub-agents：需要额外的上下文隔离、结果汇总、生命周期管理；做不好会变成“多个模型互相污染上下文”。
  • Plan mode：强制两阶段会降低简单任务的效率；而“计划”本身很难在不执行的情况下验证。

替代方案是：让用户用扩展实现自己想要的形态。这符合 pi 的定位——不是替你决定工作流，而是给你拼装工作流的零件。代价是初次使用需要更多判断；收益是不会被框架的假设锁死。

11.10评价：什么时候该用 pi

pi 适合：

  • 想要一个可读、可改、无 magic 的 coding agent 核心；
  • 愿意自己写扩展来适配工作流；
  • 能接受“安全靠容器化”的运维前提；
  • 重视会话可恢复、可分支、可审计。

不太适合：

  • 需要开箱即用的企业审批流与细粒度权限；
  • 需要内置的多 agent 编排与可视化工作流编辑器；
  • 团队完全没有 Node/TypeScript 维护能力。

设计 harness 时，最值得抄的不是某个具体实现，而是它的分层与契约：把模型调用、循环、工具、上下文、接口分开；把“不得抛异常”“失败要可恢复”“原始记录不可变”写成明确规则。这些规则比任何 prompt 技巧都更影响长期可用性。
